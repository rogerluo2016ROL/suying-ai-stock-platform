# ADR-015.0: `_pg_write` UPSERT 扩展 —— path #4 子 ADR 前置

- 状态：**Accepted**（2026-06-22 tech-lead 自实施 + SIT 9/9 pass，覆盖默认零回归 + 真实 UPSERT 写库 + 4 类 ValueError 防误用）
- 日期：2026-06-22
- 决策者：tech-lead 起草；product-lead 单实例授权
- 影响范围：`_pg_write` thin wrapper + `_insert_rows` 主干 + 单测；零 sync 模块改动
- 父 ADR：ADR-015 §决策 3 「方案 A 推荐」+ §决策 4 「P0 前置」

## 上下文

ADR-015 盘点报告 §4 + §5 已确定：path #4 inline executemany 8+ 模块要按方案 A 渐进切换到 `_pg_write` 主干。但 path #4 模块中有 2 个高频写入模块（**stocks.py / namechange.py**）的 SQLite 侧用 `INSERT OR REPLACE`，PG 侧用 `inline-cursor` 显式 `ON CONFLICT(...) DO UPDATE SET ...`，**业务语义是 UPSERT**（部分列每日变化，如 stocks.name 名称更换 / status 上市状态变更 / namechange.start_date 区间续接）。

`_pg_write` thin wrapper 现状只支持 `ON CONFLICT DO NOTHING`（沿用 ADR-012 §决策 5.2 「依赖表 PK 约束 + DO NOTHING」），切 path #4 模块若直接换路径会**改变业务语义**：

- `stocks.py:85` `INSERT INTO stocks(...) ON CONFLICT(code) DO UPDATE SET name=EXCLUDED.name, status=EXCLUDED.status, list_date=EXCLUDED.list_date` → 切 `_pg_write` 后退化为 DO NOTHING → 名称 / 状态变更**永远不更新**
- `namechange.py:123` `INSERT INTO st_history(...) ON CONFLICT(code, ann_date) DO UPDATE SET start_date=EXCLUDED.start_date, end_date=EXCLUDED.end_date, change_reason=EXCLUDED.change_reason` → 退化后 ST 区间续接失效

这是 ADR-015.1 / 015.5 实施的硬阻塞。本 ADR 解锁前置。

### 不做此决策的后果

1. ADR-015.1（stocks.py）/ADR-015.5（namechange.py）无法启动，path #4 P1 优先级模块阻塞
2. 若两个子 ADR 强行切换 → 业务回归（stock name 永远停在首次同步快照 / ST 区间错误）
3. 若不切换 → ADR-015 收尾期延长，inline-cursor 反模式长期残留

### 决策 1：API 设计

`_insert_rows` 函数签名：

```python
def _insert_rows(
    db: _Db, table: str, columns: list[str],
    rows: list[tuple],
    retries: int = 0,
    data_volume_floor: int | None = None,
    data_volume_warn: int | None = None,
    # ADR-015.0 新增 ─────────
    conflict_action: Literal["nothing", "update"] = "nothing",
    conflict_cols: list[str] | None = None,
    update_cols: list[str] | None = None,
    now_cols: list[str] | None = None,
) -> int:
```

行为契约：

| `conflict_action` | `conflict_cols` | `update_cols` | `now_cols` | 生成 SQL |
|---|---|---|---|---|
| `"nothing"`（默认） | 任意 | 任意 | 任意 | `ON CONFLICT DO NOTHING`（沿用旧行为，100% 向后兼容） |
| `"update"` | 必传（非空） | 必传（非空） | None | `ON CONFLICT (cc) DO UPDATE SET {uc=EXCLUDED.uc}` |
| `"update"` | 必传 | 必传 | 非空 | `ON CONFLICT (cc) DO UPDATE SET {uc=EXCLUDED.uc}, {nc=NOW()}` |
| `"update"` | None / 空 | 任意 | 任意 | **raise ValueError** |
| `"update"` | 任意 | None / 空 | 任意 | **raise ValueError** |

**关键设计点**：

1. **默认值零行为变化**：`conflict_action="nothing"` 不传 → SQL 与旧版字面一致 → 31 个现有 `_pg_write` 调用方零回归
2. **`update_cols` 必须显式传**：不允许 `update_cols=None` 隐式更新所有列（防业务列 / 审计列 / PK 列混入 EXCLUDED 时的语义错位）
3. **`conflict_cols` 必须显式传**：DO UPDATE 必须指定冲突约束，依赖隐式 PK 不安全（表可能有多个 UNIQUE）
4. **`update_cols` ⊆ `columns`**：实施时校验，越界 raise ValueError（防写错列名静默生成 NULL）
5. **自动列过滤前置**：先按 `_get_pg_columns(table)` 过滤 `columns` / `update_cols` / `conflict_cols` / `now_cols`，四者都过滤后再生成 SQL（沿用现有自动过滤防 schema drift）
6. **`now_cols`（minor amend 2026-06-22）**：独立追加列（**不要求 ⊆ `columns`**），INSERT VALUES 和 DO UPDATE SET 都走 `NOW()` 而非 `EXCLUDED.x` / 业务值。专为 `updated_at` 设计 —— §决策 2 约束 3 黑名单禁止 `updated_at` 走 EXCLUDED（防业务值污染审计语义），但 stocks / namechange 业务上需要每次 UPSERT 刷新 "最后同步时间"（`MONITORED_TABLES["stocks"].date_col="updated_at"` gap_threshold=7d，不刷新 → detect_data_gaps 误报）。实现上通过 `execute_values` 的 `template` 参数在 VALUES 里混 `NOW()` 字面量，`now_cols` 追加到 INSERT columns 末尾。约束：`now_cols` ∩ `columns` = ∅（独立追加，不重复）；`now_cols` ∩ `update_cols` = ∅；`now_cols` ∩ `conflict_cols` = ∅；`now_cols` ⊆ 表实际列（schema 过滤）。仅在 `conflict_action="update"` 时生效，`"nothing"` 时忽略。

`_pg_write` 函数签名（仅新增透传）：

```python
def _pg_write(
    table: str, columns: list[str], conflict_cols: list[str],
    rows: list[tuple],
    # ADR-015.0 新增 ─────────
    conflict_action: Literal["nothing", "update"] = "nothing",
    update_cols: list[str] | None = None,
    now_cols: list[str] | None = None,
) -> int:
```

8 个 `write_*` helper 不需要任何改动（默认 `conflict_action="nothing"` 沿用旧行为）。

### 决策 2：实施约束

**5 项硬约束**：

1. **零现有调用方回归**：grep 全 repo `_pg_write\(|_insert_rows\(`，所有现有调用点不传 `conflict_action` → 必须保持旧行为字面一致
2. **`update_cols` 不允许包含 `conflict_cols`**：实施时 assert `set(update_cols) & set(conflict_cols) == set()`，违反 raise ValueError（PK 列 DO UPDATE SET 是反模式）
3. **`update_cols` 不允许包含审计列 `created_at` / `updated_at`**：grep 实证两列在 14 张表存在；若传入 → raise ValueError（防 created_at 被刷新破坏审计语义；updated_at 应由 trigger 自动维护或在 SQL 显式 `updated_at = NOW()` 不走 EXCLUDED）
4. **SQLite 路径零改动**：分支内只处理 `db._pg`；`else` 分支 `INSERT OR REPLACE` 保持现状（SQLite 本身就 UPSERT，无歧义）
5. **测试覆盖率 ≥ 4 用例**：nothing 默认 / update 成功 / update 缺参数 raise / update_cols 含 conflict_cols raise

## 备选方案

- **A. 新增独立 `_pg_upsert` 函数**（与 `_pg_write` 同型，但走 DO UPDATE） —— pros: 默认参数零变化；cons: 8 个 `write_*` helper 部分需新增 `write_*_upsert` 双胞胎（stocks / namechange / 可能还有 stock_profiles 未来），代码膨胀；**否决**
- **B. 改造 `_pg_write` 默认变 UPSERT** —— pros: 简化 API；cons: 31 个现有调用点全部需要 audit 业务语义是否真的要 UPSERT，工作量爆炸，回归风险极高；**否决**
- **C. 把 UPSERT 逻辑下推到调用方** —— pros: 主干 0 改动；cons: 等于不做 ADR-015，回到 inline-cursor，path #4 治理失败；**否决**
- **D（推荐）**：`_pg_write` / `_insert_rows` 加可选 `conflict_action` 参数 —— pros: 默认参数兜底零回归 + API 统一 + 主干扩展；cons: 函数签名变长（5 → 8 参数）；**采纳**

## 影响

### 正面

- ADR-015.1（stocks.py）/ ADR-015.5（namechange.py）解锁，可以启动
- `_insert_rows` 成为 PG 写入唯一主干，path #2 / #3 / #4 大一统
- API 统一后未来新 sync 模块只需调一个函数，新人成本下降

### 负面

- `_insert_rows` 函数复杂度上升（5 → 8 参数 + 3 个新分支）；缓解：单测覆盖 + ValueError 早 fail + docstring 详尽
- `update_cols` 校验需要 grep `created_at|updated_at` 黑名单维护；缓解：硬编码两列，新增审计列时人工 review（频率极低）

### 中性

- 与 ADR-006 / 012 决策一致：「PG-first 直写 + `_pg_write` 是 PG 主干」自然延伸
- 不引入新依赖（仍用 psycopg2.extras.execute_values + ON CONFLICT SQL）
