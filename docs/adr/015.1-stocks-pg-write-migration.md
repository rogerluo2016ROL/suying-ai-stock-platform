# ADR-015.1: stocks.py PG 路径迁移到 `_pg_write` UPSERT

- 状态：**Accepted**（2026-06-22 tech-lead 自实施 + SIT 7/7 pass，含真实写库验证 UPSERT + updated_at 100% fill）
- 日期：2026-06-22
- 决策者：tech-lead 起草自实施
- 影响范围：`services/data-service/app/sync/stocks.py` 单文件 PG 写入路径
- 父 ADR：ADR-015 §决策 4 P1 + ADR-015.0（前置，已 Accepted）

## 上下文

ADR-015 盘点报告 §1 列 `stocks.py` 为 P1 高风险 + 高频写入模块。现状 PG 路径用 inline-cursor 逐行 `INSERT ... ON CONFLICT(code) DO UPDATE SET ... updated_at=NOW()`（`stocks.py:66-72` + `142-148` 两处），业务语义是 UPSERT（stock.name 名称更换 / is_st ST 状态变更 / list_date 上市日期）。

ADR-015.0 已为 `_pg_write` 加 `conflict_action="update"` + `now_cols` 参数，解锁 UPSERT + 审计列刷新。本 ADR 是 015.0 API 的第一个真实业务用例。

### 不做此决策的后果

1. stocks.py 保留 inline-cursor 反模式（逐行 execute，5000 行 = 5000 次 round-trip），性能差
2. 不走 `_insert_rows` 自动列过滤，schema drift 时整批失败（虽 stocks 当前无 drift，但防御性收口）
3. ADR-015 path #4 治理无首个落地用例，015.2+ 缺参考

## 决策

### 决策 0：文件改动白名单

| # | 文件 | 允许改动 |
|---|---|---|
| 1 | `services/data-service/app/sync/stocks.py` | (a) `sync_stock_list` PG 路径 inline-cursor → `_pg_write(update)`；(b) `sync_stocks_incremental` 同样；SQLite 路径保留 `INSERT OR REPLACE`（方案 A 决策） |
| 2 | `docs/adr/015.1-stocks-pg-write-migration.md` | 本 ADR |
| 3 | `progress/tech-lead.md` | SIT 段 |

**禁止**：pg_writer.py / etl.py / scheduler.py / SQLite 路径 / 任何其他 sync 模块。

### 决策 1：`_pg_write` 调用契约

```python
from app.sync.pg_writer import _pg_write

pg_written = _pg_write(
    "stocks",
    columns=["code", "name", "board", "industry", "listed_date", "is_st"],
    conflict_cols=["code"],
    rows=rows,  # [(code, name, board, industry, listed_date, is_st), ...]
    conflict_action="update",
    update_cols=["name", "board", "industry", "listed_date", "is_st"],
    now_cols=["updated_at"],
)
```

语义对照（与原 inline SQL 100% 等价）：

| 原 inline SQL 子句 | _pg_write 参数 |
|---|---|
| `ON CONFLICT(code)` | `conflict_cols=["code"]` |
| `DO UPDATE SET name=EXCLUDED.name, board=..., industry=..., listed_date=..., is_st=...` | `update_cols=[5 业务列]` |
| `updated_at=NOW()` | `now_cols=["updated_at"]` |
| 逐行 `cur.execute` | `execute_values` 批量（5000 行 1 次 round-trip） |

`code` 是 PK，不在 `update_cols`（约束 2：update_cols ∩ conflict_cols = ∅）。`updated_at` 不在 `columns`（now_cols 独立追加）。

### 决策 2：返回值语义

`_pg_write` 返回 `written`（实际影响行数，含 INSERT + UPDATE）。原 inline 代码 `pg_written += 1` 是逐行计数（无论 INSERT 还是 UPDATE 都 +1）。`execute_values` 的 `rowcount` 在 UPSERT 时报总影响行数（INSERT 算 1，UPDATE 算 1），与原语义一致。

`sync_stock_list` 返回 dict `{"pg_written": N, ...}`，N 现在是 `_pg_write` 返回值（总影响行数），与原 `pg_written += 1` 累加值语义等价。

### 决策 4：回滚点

| Checkpoint | 触发 | 动作 |

| RB-1 | `_pg_write` 返回 0 但 rows 非空 | 检查 conflict_cols 是否表 PK；检查 schema drift |
| RB-2 | updated_at 未刷新 | 检查 now_cols 传参；检查表 updated_at 列存在 |

## 备选方案

- **A. 保留 inline-cursor** —— pros: 0 改动；cons: ADR-015 path #4 治理失败，性能差；**否决**
- **B. 改 DO NOTHING** —— pros: 简单；cons: 业务回归（name/is_st 永不更新）；**否决**
- **C. 拆 SQLite 路径也走 _pg_write** —— pros: 大一统；cons: 违反 ADR-015 方案 A 决策（SQLite 侧保留 inline，YAGNI）；**否决**
- **D（推荐）**：PG 路径走 `_pg_write(update)`，SQLite 保留 `INSERT OR REPLACE` —— 采纳

## 影响

### 正面

- stocks.py PG 路径性能提升（5000 行逐行 → 1 次批量）
- 走 `_insert_rows` 自动列过滤，schema drift 防御
- ADR-015 path #4 首个落地用例，验证 ADR-015.0 API 真实业务可用

### 负面

- 无（行为 100% 等价，仅路径切换）
