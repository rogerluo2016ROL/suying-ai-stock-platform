# ADR-014.1: init_postgres.sql 反向追认 stk_factor_pro + trade_cal DDL

- 状态：**Accepted**（2026-06-22 tech-lead 自实施 + SIT 6/6 pass，含 DDL 一致性 + 幂等性 + fresh 部署模拟）
- 日期：2026-06-22
- 决策者：tech-lead 起草自实施
- 影响范围：`services/sql/init_postgres.sql` 单文件（补 2 张表 DDL）
- 父 ADR：ADR-014 §3 子 ADR 建议（合并 14.1 stk_factor_pro + 14.2 trade_cal）

## 上下文

ADR-014 audit 报告 §2 列 2 个 high drift：`stk_factor_pro` + `trade_cal`，均为 "MONITORED 但 DB+init 双缺"。

### 复审发现（audit 报告误判修正）

audit 脚本默认查 UAT PG 16432（fresh 部署），那里确实无数据。但 dev PG 6432 实测：

| 表 | dev PG 6432 | init_postgres.sql | 行数 |
|---|---|---|---|
| stk_factor_pro | ✅ 存在（20 列：id + ts_code + trade_date + 17 因子列） | ❌ 无 DDL | 71610 |
| trade_cal | ✅ 存在（3 列：cal_date PK + is_open + pretrade_date） | ❌ 无 DDL | 1348 |

**真实 drift**：不是 "DB+init 双缺"，而是 **DB 有表有数据 + init_sql 完全缺 DDL**。fresh 部署（UAT/生产新环境）会丢这两张表 → scheduler MONITORED 监控报错 + sync 写入失败 + `_trading_days_between` 算交易日数 fallback 到自然日（保守估计，影响 backtest 精度）。

### 两表业务角色

| 表 | sync 函数 | 用途 | 风险 |
|---|---|---|---|
| stk_factor_pro | `sync_stk_factor_pro_daily` / `_backfill` (scheduler.py L553/657)，走 `_pg_write` | 股票每日技术因子（MA/MACD/RSI/BOLL/KDJ + vol_ratio/turnover_rate），下游因子计算 | fresh 部署丢表 → sync 写入失败，因子数据缺失 |
| trade_cal | 无 sync（`_DESIGN_SKIP_BACKFILL` 标记，"由其他流程维护"） | 交易日历，`_trading_days_between` (scheduler.py L264) 读它算真实交易日数 | fresh 部署丢表 → backtest 交易日数 fallback 到自然日（保守，精度下降） |

### 不做此决策的后果

1. fresh 部署（UAT/新生产环境）init_sql 不建这两张表 → stk_factor_pro sync `INSERT` 报 `relation does not exist` → `_pg_write` 静默 return 0（`_insert_rows` 自动列过滤兜底打印 WARN，但数据停滞）
2. trade_cal 丢表 → `_trading_days_between` except fallback 到自然日 → backtest 交易日缺口计算偏大（保守，可能误报 gap）
3. scheduler MONITORED 监控对这两张表持续报错（detect_data_gaps 查不存在的表）

## 决策

### 决策 0：文件改动白名单

| # | 文件 | 允许改动 |
|---|---|---|
| 1 | `services/sql/init_postgres.sql` | 补 stk_factor_pro + trade_cal 两段 DDL（按 DB 现状反向追认） |
| 2 | `docs/adr/014.1-init-sql-stk-factor-pro-trade-cal.md` | 本 ADR |
| 3 | `progress/tech-lead.md` | SIT 段 |

**禁止**：任何 sync 模块 / scheduler.py / pg_writer.py / etl.py / alembic 迁移（本 ADR 只补 init_sql，DDL 与 DB 现状字面一致，无破坏性变更，alembic 不需要新迁移——fresh 部署走 init_sql，已部署环境 DB 已有表）。

### 决策 1：stk_factor_pro DDL（按 DB 现状反向追认）

DB 实测 schema（dev PG 6432）：

```sql
CREATE TABLE IF NOT EXISTS stk_factor_pro (
    id SERIAL PRIMARY KEY,
    ts_code TEXT,
    trade_date TEXT,
    ma5 DOUBLE PRECISION,
    ma10 DOUBLE PRECISION,
    ma20 DOUBLE PRECISION,
    ma60 DOUBLE PRECISION,
    macd_dif DOUBLE PRECISION,
    macd_dea DOUBLE PRECISION,
    macd DOUBLE PRECISION,
    rsi_6 DOUBLE PRECISION,
    rsi_12 DOUBLE PRECISION,
    rsi_24 DOUBLE PRECISION,
    boll_upper DOUBLE PRECISION,
    boll_mid DOUBLE PRECISION,
    boll_lower DOUBLE PRECISION,
    kdj_k DOUBLE PRECISION,
    kdj_d DOUBLE PRECISION,
    kdj_j DOUBLE PRECISION,
    vol_ratio DOUBLE PRECISION,
    turnover_rate DOUBLE PRECISION
);
```

**注意**：DB 表无 UNIQUE(ts_code, trade_date) 约束（仅 id PK）。`sync_stk_factor_pro_daily` 调 `_pg_write(["ts_code","trade_date"], rows)` 默认 DO NOTHING，但无 UNIQUE 约束 → ON CONFLICT DO NOTHING 无冲突可检 → **重复 sync 会堆叠重复行**。这是 pre-existing 问题（71610 行可能有重复），**不在本 ADR scope**（本 ADR 只补 DDL，100% 还原 DB 现状；若需加 UNIQUE 去重，另开 follow-up issue）。

### 决策 2：trade_cal DDL（按 DB 现状反向追认）

DB 实测 schema：

```sql
CREATE TABLE IF NOT EXISTS trade_cal (
    cal_date DATE PRIMARY KEY,
    is_open INTEGER,
    pretrade_date DATE
);
```

trade_cal 有 PK(cal_date)，无 sync 函数（外部维护/手动导入）。本 ADR 只补 DDL，不新增 sync。

### 决策 3：不新增 alembic 迁移

按 ADR-007 Q-4 双轨：业务表走 init_postgres.sql，auth/audit 走 alembic。stk_factor_pro / trade_cal 是业务表，归 init_sql 轨。已部署环境（dev PG 6432）DB 已有表，init_sql `CREATE TABLE IF NOT EXISTS` 幂等不破坏；fresh 部署走 init_sql 建表。**不需要新 alembic 迁移**（与 ADR-008~013 schema 对齐 ADR 不同：那些是 DB 列名 drift 需迁移修正，本 ADR 是 init_sql 缺 DDL，纯补声明）。

### 决策 4：SIT 验证清单

| # | 验证项 | 命令 | 期望 |

### 决策 5：回滚点

| Checkpoint | 触发 | 动作 |
|---|---|---|
| RB-1 | init_sql DDL 与 DB 现状列数不一致 | 重新 `\d` 确认，修正 DDL |
| RB-2 | 已部署环境重跑 init_sql 报错 | 检查 IF NOT EXISTS 是否遗漏 |

## 备选方案

- **A. 拆 14.1 (stk_factor_pro) + 14.2 (trade_cal) 两个 ADR** —— pros: 粒度细；cons: 两表都是 init_sql 反向追认同型改动，合一个 ADR 更高效；**否决**（合并）
- **B. 新增 alembic 迁移建表** —— pros: 走 alembic 轨；cons: 业务表归 init_sql 轨（ADR-007 Q-4），且已部署环境 DB 已有表，alembic 迁移多余；**否决**
- **C. 顺手给 stk_factor_pro 加 UNIQUE(ts_code, trade_date) 去重** —— pros: 修 pre-existing 重复行问题；cons: 改变 DB 现状（加约束可能因现存重复行失败），扩 scope 违反最小变更；**否决**（另开 follow-up）
- **D（推荐）**：init_sql 补两表 DDL，100% 还原 DB 现状，不加约束不迁 alembic —— 采纳

## 影响

### 正面

- fresh 部署不再丢 stk_factor_pro / trade_cal → sync 写入正常 + 监控不报错 + `_trading_days_between` 精确
- ADR-014 audit 2 个 high drift 清零

### 负面

- 无（纯补声明，DDL 与 DB 现状字面一致，幂等）

### 遗留（不在本 ADR scope）

- stk_factor_pro 无 UNIQUE 约束 → 重复 sync 堆叠重复行（pre-existing，另开 follow-up issue）
- trade_cal 无 sync 函数 → 需手动导入/外部维护（pre-existing，不在本 ADR scope）
