# ADR-015.2: tushare.py PG 路径收口审计 — no-op 确认

- 状态：**Accepted**（2026-06-22 tech-lead 自审计 + SIT 6/6 pass，结论：PG 路径已在 ADR-012 期间收口，无需改造）
- 日期：2026-06-22
- 决策者：tech-lead 起草自审计
- 影响范围：**audit-only，零代码改动**
- 父 ADR：ADR-015 §决策 4 P1

## 上下文

ADR-015 盘点报告 §1 / §2 将 `tushare.py` 列为 P1 高风险模块，标注 "5 处 inline executemany"（L66 / L186 / L194 / L265），理由是 "大表 daily_kline / moneyflow / stk_limit / limit_list_d 影响下游"。本 ADR 是实施前审计，核实是否真的需要改造。

### 审计发现

grep 实证（`services/data-service/app/sync/tushare.py`）：

1. **PG 直连 = 0**：全文无 `psycopg2` / `conn.cursor()` / `conn.execute()` / `cur.execute(...INSERT...)` 任何 PG 直连代码
2. **PG 写入全部走 `write_*` helper**：7 处 import，覆盖 7 张表

| 行 | helper | 表 | delegate 到 |
|---|---|---|---|
| L59-60 | `write_daily_kline` | daily_kline | `_pg_write` (ADR-012 §5.2) |
| L166-167 | `write_moneyflow` | moneyflow | `_pg_write` |
| L173-174 | `write_stk_limit` | stk_limit | `_pg_write` |
| L216-217 | `write_index_daily` | index_daily | `_pg_write` |
| L252-253 | `write_daily_basic` | daily_basic | `_pg_write` |
| L255-256 | `write_ths_daily` | ths_daily | `_pg_write` |
| L289-290 | `write_limit_list_d` | limit_list_d | `_pg_write` |

3. **盘点报告的 "5 处 inline executemany" 全是 SQLite 侧**：L66 / L186 / L194 / L226 / L265 / L299（实际 6 处，盘点报告少算 L226 index_daily SQLite 逐行 execute）

| 行 | 表 | 路径 | 方案 A 决策 |
|---|---|---|---|
| L66 | daily_kline | SQLite `executemany` | 保留 |
| L186 | moneyflow | SQLite `executemany` | 保留 |
| L194 | stk_limit | SQLite `executemany` | 保留 |
| L226 | index_daily | SQLite 逐行 `execute` | 保留 |
| L265 | daily_basic / ths_daily | SQLite `executemany` | 保留 |
| L299 | limit_list_d | SQLite 逐行 `execute` | 保留 |

### 结论

**tushare.py PG 路径已在 ADR-012 §决策 5.2 期间（thin wrapper 化）完成收口**，盘点报告将其列为 P1 是**误判**——报告 §2 矩阵的 "PG 路径" 列已正确标注 `_pg_write (via thin wrapper)`，但 §决策 4 排期表仍按 "inline" 列为 P1，两处不一致。

按 ADR-015 方案 A 决策：「SQLite 侧保留 inline 是合理的（YAGNI）」，SQLite 侧 6 处 inline executemany **保留不动**。

### 决策 1：no-op 声明

- PG 路径：8 处 `write_*` helper → `_pg_write`（已收口，ADR-012 期间完成）
- SQLite 路径：6 处 inline executemany / execute（按方案 A 保留）

### 决策 3：盘点报告修正建议

ADR-015 §决策 4 排期表将 tushare.py 列为 P1 "5 处 inline" 是基于盘点报告 §1 的 `executemany` 行号（L66/L186/L194/L265），但这些行号是 **SQLite 侧**。本 ADR 修正认知：

- tushare.py 的 PG 改造**已在 ADR-012 完成**，不属于 ADR-015 path #4 治理范围
- ADR-015 path #4 真正未收口的模块是 `stock_profiles.py`（PG 走 `inline-execute_values`，未走 `_pg_write`）+ `namechange.py`（PG 走 `inline-cursor`）+ `etl_rt_k.py`（PG 走 `inline-execute_values`）

建议 ADR-015.4 把 `stock_profiles.py` 提到 P1（原 P2），因为它是 path #4 里 PG 侧仍未收口的高风险模块（16 列 + execute_values）。

## 备选方案

- **A. 强行把 SQLite inline 也收口** —— pros: 大一统；cons: 违反 ADR-015 方案 A 决策（SQLite 保留 YAGNI）+ 无 PG 收口收益（PG 已收口）；**否决**
- **B. 把 tushare.py 从 ADR-015 跟踪表移除** —— pros: 清洁；cons: 丢失 "已审计确认" 痕迹；**否决**（保留为 Accepted audit ADR 更可追溯）
- **C（采纳）**：写 audit-only ADR 记录 "PG 已收口 + SQLite 保留 + 盘点报告误判修正"，零代码改动
