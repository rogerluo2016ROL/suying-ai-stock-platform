### 2.2 `_insert_rows` 改造 (决策 5.1) — ⚠️ approve with concerns

**逐条核 etl.py:168-242**：

✅ 向后兼容：`max(1, retries)` 保证 `retries=0` 默认值时仍跑 1 次（旧行为 byte-equivalent）
✅ 只对 `psycopg2.OperationalError` 重试（IO 抖动），其他 SQL 错误立即 WARN+return 0（retry 不掩盖代码 bug，符合 ADR §决策 5.1.b）
✅ 指数退避 1s/4s/16s 与 pg_writer 原策略一致
✅ data_volume_floor 仅 PG 路径触发（SQLite 本地文件无 IO 抖动，符合 §决策 5.1.c）
✅ `import time` / `import psycopg2` lazy 在函数体内，不影响 SQLite-only 环境
⚠️ **W-2 (warning)**: `_VOLUME_FLOOR_MAP` 单档替代了原 `_check_data_volume` 的双档分级——旧函数对 daily_kline / stk_mins 同时有 `<1000 ERROR` + `<3000 WARN` 两档；新 `data_volume_floor=1000` 只剩 ERROR 档，**1000-3000 之间的偏低写入"温和告警"被静默吃掉**（pg_writer.py:90 的 `<3000 WARN` 仅 `_check_data_volume` 函数内部，已成 dead code 见 S-2）。
- 影响：日线 fetched=1500 这种"上半场断网"场景从 `logger.warning` 降级为"没声音"。
- 修复建议：在 `_insert_rows` `data_volume_floor` 之上加一个 `data_volume_warn` 二档参数（或保持 `data_volume_floor` 含义为单档 ERROR + 在 pg_writer thin wrapper 内额外调一次 `_check_data_volume` 兜底 WARN）。不阻断 merge——daily_kline / stk_mins 实测量级都在 5000+，warn 档触发概率小，但应作为 follow-up 在 ADR-013/014 顺手补回。

### 2.3 `_pg_write` thin wrapper (决策 5.2) — ⚠️ approve with concerns

**逐条核 pg_writer.py:33-76**：

✅ 8 个 write_* helper 函数体零改动，业务列重排（write_moneyflow 跳 net_mf_vol 第 12 列 / write_daily_basic 重排 8 字段等）完全保留
✅ `conflict_cols` 参数语义保留但内部不传给 `_insert_rows`——ADR §决策 5.2.bis 论证 `ON CONFLICT DO NOTHING`（无 target）与原 `ON CONFLICT(cols) DO NOTHING` 在 PG 语义下等价或更宽容（target-less 版本对任意 unique constraint 都跳）。**实测前提：所有调用方传的 conflict_cols 都 ⊆ 表 PK/UNIQUE 约束**，本次审查 grep 抽样 write_stk_mins/write_daily_kline/write_moneyflow 等 8 个 helper 全部满足。
✅ `_VOLUME_FLOOR_MAP` 显式策略表（仅 daily_kline / stk_mins 1000 floor），其他表 None=关闭
✅ sys.path 注入 packages/kronos-data 路径（独立 import 不依赖 scheduler.py 先加载）
✅ Lazy import `from kronos_data.etl import _insert_rows, _get_etl_db` 避免循环依赖

⚠️ **W-1 (warning)** — **共享连接被反复关闭**：
- 位置：`pg_writer.py:60-76`
- 问题：`_get_etl_db()` 在 `etl.py:149-158` 用模块级缓存 `_pg_conn`；同一进程内首次调用建连接 → 缓存。`_pg_write` 在 `finally: db.close()` 里关闭这个**模块级缓存连接**。下次 etl.py 任何 sync 函数（如 `sync_top_inst`）调 `_get_etl_db()`，检测到 `_pg_conn.closed` 后重连——功能正确，但**完全废除了连接缓存意图**，每批写入都付重连开销（PG 本地 ~5-15ms × 数千批）。
- 复现：跑 `data-service` 完整 daily cron（含 write_daily_kline / write_moneyflow 多次 + etl.sync_X 多次），观察 PG `pg_stat_activity` 在 1 个稳定连接还是反复 connect/disconnect。
- 修复建议（择一）：
  1. **简单**：`_pg_write` 不关连接（去掉 `finally: db.close()`），交由调用方或进程退出时关
  2. **正确**：给 `_get_etl_db()` 加 `borrow=False` 参数，`_pg_write` 用 `borrow=True` 拿一个**临时连接**（不进缓存）
- 不阻断 merge：scheduler.py 改造前 pg_writer._pg_write 自建 psycopg2.connect 每次也是新连接，新代码至少**没变差**，但放弃了改造潜在收益。优先级 P1 follow-up。

⚠️ **S-2 (suggestion)** — `_check_data_volume` 是 dead code：
- pg_writer.py:79-92 函数无人调用（thin wrapper 已直接走 `_insert_rows` 的 data_volume_floor）。
- 与 W-2 联动：旧 `<3000 WARN` 分级活在这函数里，建议删函数 + 在 _insert_rows 加 warn 档（W-2 修复方案 1），或者改 `_pg_write` 在 wrapper 调用前后调一次 `_check_data_volume` 兜底 WARN（W-2 方案 2 + 保留函数）。
- 不阻断 merge。
