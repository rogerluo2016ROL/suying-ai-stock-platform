### P2-2 — _COLUMN_MAP 扩 vol→volume + 偏离审计字面建议（认可）

**独立核实**：
- `_COLUMN_MAP` 加 `"vol": "volume"`，作用在 `execute()` 的 **SQL 文本翻译**（L96-97 `re.sub(rf'\b{re.escape(old)}\b', new, sql_pg)`）—— 把 SQLite/engine 列名 `vol` 翻译成 PG 列名 `volume`，针对的是**读路径的 SELECT 文本**。
- 审计 P2-2 字面建议"扩 _COLUMN_MAP **去 write_index_daily 手补重排**"—— dev 正确识别这混淆了两个机制：
  - `_COLUMN_MAP`（SQL 文本翻译，读路径）；
  - `write_*` 函数的行元组按 PG 列序重排（值级，写路径）。
  - 两者层次不同，**无法互相替代**。删 write_* 重排会导致数据错位（值落入错误列）。
- dev 的修复：扩 `_COLUMN_MAP` 加 `vol→volume`（合理的防御性扩展）+ **保留** write_* 重排 + 加注释明确层次区别。
- **实读确认**：当前 `pg_adapter` 自身的 SELECT（`get_kline` L168/L174）已用 PG 原生 `volume`，所以 `vol→volume` 翻译当前不被 pg_adapter 内部触发——它是为"未来 engine 侧写 SQLite 风格 SQL 含 `vol` 时透明翻译"的防御性覆盖。审计选项 A（明确防御性扩展），scope 正确。
- kronos-factors 31 passed（dev 声称）/ 实测见 W-2。

**偏离审计字面建议认可**：dev 没盲从审计后半句（"去手补重排"），正确区分了 SQL 文本翻译 vs 行值重排两个机制，保留必要的 write_* 重排 + 注释说明。这是准确的工程判断。

### P2-4 — gateway _forward_headers 透传 ✅

- 新增 `_HOP_BY_HOP` 集合：RFC 7230 §6.1 hop-by-hop（connection/keep-alive/proxy-*/te/trailers/transfer-encoding/upgrade）+ body-encoding（content-length/content-encoding/content-type）。
- `_forward_headers(upstream_headers)`：strip `_HOP_BY_HOP` + 用 `get_all("Set-Cookie")` 保留多值（HTTPMessage Multimap）+ 输出 `out["Set-Cookie"] = list(cookies)`（Starlette Response headers 接受 list 值）。
- gateway 200 分支（L189）+ HTTPError 分支（L207）都调 `_forward_headers`。
- **正确性核实**：
  - body-encoding headers 必须剥（urllib 已 read+decode body，re-emit content-length/encoding 会 corrupt 下游响应）✓；
  - content-type 剥（由 `Response(media_type=...)` 设，避免 duplicate header）✓；
  - Set-Cookie 多值保留（refresh_token rotation 场景 backend 可能下多个 cookie）✓；
  - 有 `hasattr(upstream_headers, "get_all")` 防御（http.client HTTPMessage 有 `get_all`，HTTPError.headers 同型）✓。
- dev 的 email.message 模拟 smoke（X-Request-ID 透传 / Set-Cookie 双值全保留 / hop-by-hop 被剥）覆盖关键路径。
