## Findings

### Suggestion

#### S-1 — main.tsx 最外层 ErrorBoundary 的默认 fallback 无 antd ConfigProvider 上下文
- **位置**: `frontend/src/main.tsx:59-63`（`<ErrorBoundary>` 在 `<ThemeProvider>` 外层）
- **问题**: 最外层 ErrorBoundary 是全站最后防线，若 `<ThemeProvider>` 或 `<ConfigProvider>` 自身抛错（如 localStorage 不可用导致 ThemeProvider 初始化异常），其默认 fallback `<Result>` 会无 antd locale/theme 上下文渲染（中文 locale 退化、主题 token 缺失）。实际概率极低（providers 几乎不抛错），但层级上 fallback 在 ConfigProvider 之外。
- **严重性**: suggestion —— 非 bug（providers 抛错是极罕见边缘），仅层级提示。
- **修复建议**: 给最外层 ErrorBoundary 传一个**不依赖 antd 的纯 HTML 自定义 fallback**（`<ErrorBoundary fallback={() => <div style="...">页面崩溃，请<a href="/">刷新</a></div>}>`），确保根级兜底在无 ConfigProvider 时也能渲染。可选优化，不阻塞。

#### S-2 — `client.ts` `healthApi.check` 的 `.catch(() => ({ data: { status: 'offline' } }))` 吞错并伪造成功响应
- **位置**: `frontend/src/api/client.ts:219-220`（`healthApi.check` / `healthApi.gateway`）
- **问题**: 健康检查的 catch 把任何错误（含网络错误、超时、CORS）转换成一个**看似成功的 `{ data: { status: 'offline' } }` 响应对象**。调用方（如 Dashboard 健康卡片）拿到的是 resolved promise + 200 形态 data，无法区分"服务 offline"与"请求本身失败（网络断开）"。这是"吞错伪装成功"反模式 —— 虽然语义上 offline 是期望结果，但调用方若做 `.then(r => r.data.status === 'online')` 会正常工作，若做 try/catch 则永远进不到 catch。
- **严重性**: suggestion —— 健康检查场景下"offline = 请求失败"是合理等价（服务不可达即视为离线），当前实现可工作。但伪装成功响应破坏了 axios 错误契约，下游若扩展（如区分 timeout vs offline）会踩坑。
- **修复建议**: 改为 `healthApi.check` 内部 catch 后 throw 一个语义化错误（如 `throw new HealthCheckError(service)`），或返回 `{ data: { status: 'offline' }, _failed: true }` 显式标记。非本 task 范围，可归入 FE-P2 技术债。
