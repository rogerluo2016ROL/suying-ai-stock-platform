## Warning（建议修复）

- [ ] **`frontend/src/components/auth/ProtectedRoute.tsx:37` — 403 页面"返回首页"按钮使用 `window.location.href` 进行整页跳转**

  **问题**: `onClick={() => window.location.href = '/'}` 触发完整的页面重载，导致：
  1. React 状态树被销毁重建（AuthContext 重新初始化，再次触发 refresh → /me 流程）
  2. 丢失 SPA 导航的流畅体验
  3. 用户可能看到加载闪烁

  **复现步骤**:
  1. 以 `user` 角色登录
  2. 访问 `/admin/users`
  3. 点击 403 页面上的"返回首页"
  4. 浏览器整页刷新，而非 SPA 路由跳转

  **修复建议**:
  ```tsx
  // 使用 useNavigate 替代 window.location.href
  import { useNavigate } from 'react-router-dom';

  export default function ProtectedRoute({ children, roles }: ProtectedRouteProps) {
    const navigate = useNavigate();
    // ...
    extra={
      <Button type="primary" onClick={() => navigate('/', { replace: true })}>
        返回首页
      </Button>
    }
  ```

- [ ] **`frontend/src/components/auth/LoginPage.tsx:17-20` 和 `RegisterPage.tsx:16-19` — 在 render 阶段直接调用 `navigate`**

  **问题**: `if (isAuthenticated) { navigate('/', { replace: true }); return null; }` 在组件 render 阶段（而非 `useEffect`）调用 `navigate`。React 18 Strict Mode 下，render 可能被多次调用而不提交，导致导航副作用被触发多次，且 React 可能在控制台发出 warning（"Cannot update a component while rendering a different component"）。

  **复现步骤**:
  1. 登录成功后访问 `/login`
  2. React 18 Strict Mode 下组件 double-render
  3. `navigate` 在 render 阶段触发，可能导致导航后仍短暂渲染登录表单

  **修复建议**:
  ```tsx
  // LoginPage.tsx
  useEffect(() => {
    if (isAuthenticated) {
      const redirect = searchParams.get('redirect') || '/';
      navigate(redirect, { replace: true });
    }
  }, [isAuthenticated, navigate, searchParams]);

  if (isAuthenticated) return null;
  ```

- [ ] **`frontend/src/App.tsx:126-133` — 未登录用户渲染的降级 Routes 树存在路由覆盖缺口**

  **问题**: 当 `!isAuthenticated` 时，`App.tsx` 渲染仅含 `LoginPage` 和 `RegisterPage` 的有限 Routes 树，但 `isAuthPage` 判别依赖 `location.pathname`（`/login` 或 `/register`）。如果用户直接访问 `/settings` 这类仅管理员可访问的路由，未登录时：
  1. `isAuthPage` = false
  2. `!isAuthenticated` = true
  3. 进入有限 Routes block → `/settings` 不匹配 → fallback 到 `<LoginPage />`
  4. 登录后 `searchParams` 中无 `redirect` 参数（因为 `*` 路由未传递 `redirect`）→ 用户不会跳回 `/settings`

  **复现步骤**:
  1. 清除所有 cookie，访问 `/settings`
  2. 看到登录页，登录成功
  3. 跳转到 `/`（首页）而非 `/settings`

  **修复建议**: 在 `*` 路由中使用与 ProtectedRoute 一致的 redirect 模式：
  ```tsx
  // Option: 用 Navigate 替代直接渲染 LoginPage
  <Route path="*" element={<Navigate to={`/login?redirect=${encodeURIComponent(location.pathname)}`} replace />} />
  ```

- [ ] **`frontend/src/contexts/AuthContext.tsx:83-89` — `injectAuth` useEffect 依赖 `accessToken`，每次 token 变更都重新注册拦截器闭包**

  **问题**: `injectAuth` 在 `useEffect` 中随 `accessToken` 变更反复调用。虽然 `injectAuth` 本身只是替换模块级闭包引用（O(1) 操作），但每次调用 create 新的箭头函数传给 axios 拦截器（拦截器已注册，不会重复）。功能上正确，但造成不必要的垃圾回收压力和语义误导（inject 语义上是"注入一次"，实际是"每次 token 变化重新注入"）。

  **修复建议**: 将 `injectAuth` 调用移到初始化 useEffect（仅 on mount），getter 函数直接读取模块级 ref：
  ```tsx
  const accessTokenRef = useRef(accessToken);
  accessTokenRef.current = accessToken;

  useEffect(() => {
    injectAuth(
      () => accessTokenRef.current,  // 通过 ref 读取最新值
      doRefresh,
      doForceLogout,
    );
  }, []);  // 仅 on mount
  ```

## Suggestion（可选优化）

- [ ] **`frontend/src/contexts/AuthContext.tsx:54-67` — `doRefresh` 在 refresh 成功后额外调用 `/me` 获取用户信息**

  **问题**: Refresh 流程需要 2 次 API 调用（refresh → `/me`），增加了网络延迟和失败点。如果 refresh 端点直接返回 user info（类似 login/register），可节省一次往返。当前后端 refresh 端点 `AuthTokenResponse` 仅返回 `access_token` + `expires_in`。建议与 backend-dev 协商，在 refresh 响应中增加可选的 user 字段。

- [ ] **`frontend/src/components/auth/RegisterPage.tsx:66` — 前端 name 校验 min:2/max:20，后端 Pydantic 校验 min:1/max:50**

  **问题**: 前后端校验参数不一致（前端 2-20 字符，后端 1-50 字符）。后端是真实防线，前端校验可宽松于后端但不能严于后端——当前前端过严（min:2 vs 1），1 字符的用户名在后端合法但前端拦截。虽然单个字符的用户名不常见，但契约应一致。

  **修复建议**: 将前端 name 校验 min 改为 1，或更新后端 Pydantic schema 为 min_length=2。

- [ ] **`frontend/src/api/client.ts:7` — axios baseURL 硬编码为 `/api/v1`**

  **问题**: 如果将来需要对接不同环境的后端（如 staging vs production），baseURL 无法动态切换。当前 Vite proxy 在开发环境下有效，但生产环境可能需要完整域名。

  **修复建议**: 使用环境变量驱动 baseURL：
  ```tsx
  const api = axios.create({
    baseURL: import.meta.env.VITE_API_BASE_URL || '/api/v1',
    // ...
  })
  ```
