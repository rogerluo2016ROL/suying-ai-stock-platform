## reserve 语义专项结论（最高风险，交易资金风控）

### 结论：设计正确，**不建议升级 tech-lead**

#### 为什么 reserve 语义是正确选择（而非纯查询 + 信号量等替代）

AC-4 要求 "并发 `asyncio.gather(can_trade, can_trade)` 在 HALF_OPEN 恰一次 True"。**纯查询 + 锁无法满足**：两次并发调用各自持锁查询 `probing_count == 0`，第一次返回 True 释放锁，第二次再持锁仍看到 `probing_count == 0`（因为没人改它）→ 两次都 True。

要恰一次 True，授予方必须在**授予的同时**改变状态让后续调用观察到"已授予"—— 即 **check-and-reserve**。这是闭式论证，无其它实现路径。

**信号量替代方案评估并否决**：`asyncio.Semaphore(1)` 语义是"资源池许可"，而 HALF_OPEN 探测不是池化资源，是**单次状态转换**（探测成功 → NORMAL，探测失败 → TRIGGERED）。用信号量会把"状态机的一次性转移"伪装成"可重复获取的许可"，破坏状态机语义（成功探测后名额已用尽，信号量却可 release 复用，导致二次探测）。reserve 语义直接编码状态机不变量，是更精确的建模。

#### TOCTOU 覆盖完整性

- **HALF_OPEN**：reserve 语义 + `_lock` 串行化 → 恰一次 True，TOCTOU 闭合（test_half_open_concurrent / high_concurrency 16 路 / sequential 三测验证）。
- **TRIGGERED**：`can_trade` L222 直接返回 False，无 mutation；并发 8 路 `test_triggered_blocks_concurrent_trades` 全 False。
- **NORMAL**：`can_trade` L212-213 直接 True，无 reservation（NORMAL 不消耗名额）；并发 5 路 `test_normal_allows_concurrent_trades` 全 True，`probing_count` 不变。
- **阈值并发触发**：`test_threshold_trigger_under_concurrency` 验证并发 `check_daily_loss` 不双触发、不丢更新。

无遗漏的 TOCTOU 分支。

#### record_probe 与 reserve 自洽性

- `can_trade` reserve（`probing_count 0→1`）→ `record_probe` 只记录 success/failure + 转状态，**不再递增** count。
- 测试 `test_record_probe_does_not_double_count_after_reservation` 断言 reserve+success 后 `probing_count == 1, probing_success == 1`，`test_record_probe_failed_probe_back_to_triggered` 断言失败后 `probing_count == 1`（不回 0，因名额已消耗；状态回 TRIGGERED）。
- 唯一边角：若 reserve 成功后、record_probe 调用前发生跨天 auto-reset 或并发 `reset()`，`record_probe` 因 `status != HALF_OPEN` 早返回（L239）—— 但此时 `probing_count` 已被 reset 清零，名额未泄漏，状态一致。**无泄漏路径**。

#### docstring 契约准确性

- `can_trade` docstring（L186-202）明确标注 "atomic check-and-reserve"、HALF_OPEN "first call reserves"、`record_probe` "does NOT re-increment"、reason 前缀契约（routes.py 依赖 `"HALF_OPEN"` 前缀）—— 全部与实现一致，无误导。
- 模块 docstring（L9-25）整体描述了并发模型 + reserve 契约 + DB 不锁的取舍 —— 准确。

### 唯一值得 tech-lead 知晓（非升级，记录项）

`can_trade` 现在有副作用（reserve 名额），函数名 "can_X" 语义上暗示"无副作用谓词"。**这是命名漂移，不是正确性问题**。重命名为 `try_reserve_trade` / `request_trade_slot` 更准确，但会 break routes.py + 全部 11 测试 + docstring 引用，改名 ROI 低。**作为 suggestion 记录**，不建议本 task 改。CLAUDE.md "交易核心路径契约变更须 tech-lead review"——本变更已在 Plan Mode 获 product-lead 授权（progress 记录四项审查全认可），reserve 语义是该授权范围内正确性必要修复的实现细节，未引入新架构方向，**不触发 tech-lead 强制升级**。

## Findings

### Warning

#### W-1 — `get_state` 的 `can_trade` 标志与 `can_trade` reserve 语义轻微语义漂移
- **位置**: `services/trade-service/app/circuit_breaker.py:301-303`（`get_state` 内 `can_trade_flag`）
- **问题**: `get_state` 是只读 API（返回 dict 含 `can_trade: bool`），其 `can_trade_flag` 用 `probing_count < 1` 计算，**不 reserve**。而 `can_trade()` 现在有 reserve 副作用。两者在 HALF_OPEN 且名额未用时都报 True，但 `get_state` 的 True 是"可下单（只读判断）"，`can_trade` 的 True 是"已为你锁定名额"。`/circuit-breaker` GET 端点（routes.py:487 `get_state`）的消费者若据 `can_trade: true` 推断"我接下来调 place_order 一定能下"，在并发下可能被另一请求抢走名额而 409。
- **严重性**: warning —— `get_state` 本就是只读快照 API，不做 reservation 是正确语义；问题仅在于命名重载 `can_trade` 让两接口语义不对称，易误导前端。非正确性 bug（真实下单仍走 `can_trade` 的权威路径）。
- **修复建议**: 在 `get_state` docstring 或返回 dict 加注释说明 `can_trade` 字段是"只读快照判断，不代表 reserve；实际下单以 place_order 为准"。或把字段重命名为 `can_trade_snapshot`（API 契约变更，慎选）。

### Suggestion

#### S-1 — `can_trade` 命名漂移（reserve 副作用 vs "can_" 谓词语义）
- **位置**: `services/trade-service/app/circuit_breaker.py:185` `async def can_trade`

#### S-2 — `place_order` 中 `check_daily_loss` + `can_trade` 双重评估轻微冗余
- **位置**: `services/trade-service/app/routes.py:168-169`
