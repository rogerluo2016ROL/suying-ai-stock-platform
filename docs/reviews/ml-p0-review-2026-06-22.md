## 2. 逐条核对（按 AC）

### AC-1 / M01 walk_forward 参数时序泄露 — **critical**

**位置**: `tools/walk_forward.py:46-83`（`_git_strategy_commit`）+ `:208-218`（main 调用 + 警告）+ `:298`（导出 JSON `strategy_commit`）

**现状（实现正确性核实）**:
- `_git_strategy_commit()` 记录 `commit / subject / date / dirty / error`，机制真实（git log/show/status subprocess），不是占位。✓
- main() 启动时打印 commit+date+dirty。✓
- 若 `commit 日期 > 样本外起始月 args.start` → 打印警告（line 215-217）。✓
- 导出 JSON 加 `strategy_commit` 字段供审计核对。✓

**critical 问题**:
> **警告 ≠ 机制阻断。** AC-1 字面要求是"显式记录用的策略 commit（checkout 对应时点或记录），不再用 HEAD"——`_git_strategy_commit` 满足"记录"，但 audit §3 根因 A 的**实质要求**是"参数从未来泄漏到过去"必须被**阻止**，而非仅被**报告**。

具体缺陷:
1. **循环仍调 HEAD 版本的策略模块**。`run_month` → `run_backtest_day`（tools/backtest_bi_trend.py）→ `from kronos_factors.engine.bi_trend_launch import run_bi_screening`（line 66 of audit 引用）——import 的是**当前工作区**的 bi_trend_launch.py，不是 oos_month 时点的版本。24 个 oos 月全部用同一个 HEAD 模块跑。
2. **警告可被忽略**。`print(...)` 到 stdout，不 raise、不 exit、不阻断。CI 跑 walk_forward 即使 commit 日期晚于样本外起始，仍正常产出 JSON 并标"样本外"。
3. **dirty=True 时无强约束**。若本地有未提交的 bi_trend_launch.py 修改，`_git_strategy_commit` 记录 dirty=True 但不阻止用脏版本跑样本外——这正是 AC-5 阶段1 progress 里"临时 git show 972a10f 替换跑完恢复"操作残留风险的代码层体现。

**修复建议（建议 tech-lead 评估选其一）**:
- **方案 A（最严，推荐）**: 加 `--strict-timeline` flag，`commit 日期 > args.start` 或 `dirty=True` 时 `sys.exit(2)`，CI 必须传此 flag 才算有效样本外。
- **方案 B（机制阻断）**: 每个 oos_month 循环内 `git show <commit-at-oos-month>:path/to/bi_trend_launch.py` 到临时文件 + `importlib` 动态加载该时点版本跑该月（audit §3 根因 A 明示此方案）。
- **方案 C（最低）**: 至少 `dirty=True` 时 raise（脏工作区跑样本外无意义）。

**架构升级建议**: M01 是 audit §3 根因 A（bi_trend 样本外 -1.157%/月的直接根因）的代码层修复。当前实现"记录了泄露但没阻止泄露"，与 audit "样本外三个字必须是真的" 的要求有差距。**建议升级 tech-lead 评估**：是否要求 walk_forward 在生产/CI 路径上强制 checkout 或 strict abort。本 reviewer 不替 tech-lead 决策"要不要修到方案 A/B"。
