# 速赢AI 全站新 UI 落地改造方案

日期：2026-06-28  
范围：前端、后端、模型服务、数据接口、交易接口、平台框架  
设计源：`docs/design/New design/01 PRD 文档/` 与 `docs/design/New design/02 参考原型/`

## 1. 当前结论

本轮审计后确认，当前前端没有完全按照新原型落地，核心原因不是局部样式问题，而是实现策略偏了：

1. 当前很多页面被收敛到 `frontend/src/pages/NewUiModulePage.tsx` 的通用模板中，形成“同壳换内容”的页面。这不能表达 1.x 到 16.x 原型里各页面独立的信息结构、交互、表格、图表、右侧操作面板和 P0 链路。
2. 顶部页签、页面体内状态条、P0 步骤条存在重复使用，和参考规范里“左侧只放一级模块、顶部只放当前模块功能页签、页面体不重复平台说明”的规则冲突。
3. 部分页面仍保留旧 Ant Design 管理后台形态，和新原型的交易工作台风格不一致。
4. 后端已有租户、账户、交易模式、公共对象字段和部分审计链路雏形，但很多业务对象仍停留在内存 store 或服务级散点接口，尚不能支撑云端多租户、真实数据库、真实交易闭环。
5. API Gateway 目前主要是反向代理，不是面向页面聚合的 BFF。新 UI 页面需要聚合行情、模型、候选、方案、交易、风控和数据新鲜度，继续让前端拼多个服务会导致空白、字段漂移和难以验收。

因此，后续改造目标必须从“组件美化”调整为“新原型逐页落地 + 页面数据契约 + 后端服务适配 + 模型/交易闭环”。

## 2. 产品目标态

速赢AI 应被重构为一个高密度 A 股量化交易工作台，而不是通用后台系统。

### 2.1 三类用户视角

| 用户 | 核心目标 | 首页与导航优先级 | 默认权限 |
|---|---|---|---|
| 操盘手 | 快速完成今日候选、方案、下单、风控、复盘 | 开盘决策、候选池、方案管理、交易中心、风控中心、回测分析 | 可用模拟盘；实盘需账户、券商、风控和审计放行 |
| 个人投资者 | 看懂自选、诊断个股、使用模拟交易、获得风险提醒 | 智能看板、自选跟踪、K线预测、个股诊断、模拟交易 | 默认隐藏模型训练、模型注册、系统运维；不默认开放自动实盘 |
| 系统管理员 | 管理租户、用户、数据、模型、券商通道、审计 | 平台升级、数据更新、模型训练、模型注册、运行状态、审计 | 可跨租户查看，但必须带审计原因 |

### 2.2 数据边界

| 数据类型 | 归属 | 示例 | 前端表现 | 后端要求 |
|---|---|---|---|---|
| 公共行情数据 | platform | 行情、指数、板块、资金、公告、政策、产业链公共图谱 | 标记“公共数据” | 可缓存、可共享，不带账户动作 |
| 公共模型输出 | platform | Kronos 预测快照、公共因子、模型版本、策略模板 | 显示模型版本、数据日期、置信度 | 必带 model_version、as_of、freshness |
| 账户私有数据 | tenant/user/account | 自选、候选池、方案、参数、回测配置 | 标记“账户私有” | 必带 tenant_id、owner_user_id、account_id |
| 交易私有数据 | tenant/account | 订单、成交、持仓、资金、券商状态、风控结论 | 标记交易模式和券商通道 | 强隔离、强审计、禁止前端传明文券商凭据 |
| 管理审计数据 | platform/tenant | 登录、授权、模型发布、风控放行、实盘动作 | 管理员可查 | append-only，不允许覆盖 |

## 3. 新前端落地原则

### 3.1 原型是唯一视觉源

前端必须以 `01 PRD 文档` 中每个 `*-preview.html` 为页面级目标态。`02 参考原型/design-spec.md` 是全局视觉和交互规范。

正式改版不再接受以下做法：

- 用一个通用页面模板承载多个模块的主体内容。
- 只迁移左侧导航、顶部行情条和几个卡片样式。
- 用 body 内部重复状态条解释“角色视图、数据域、账户隔离、券商模式、云端基线”。
- 顶部页签跳转到其他一级模块，或与页面内二级 tab 重复。
- API 无数据时渲染大片空白。

### 3.2 前端结构

目标前端分为四层：

1. `AppShell`：左侧一级导航、顶部行情带、角色/租户/账户/交易模式、系统状态入口。
2. `ModuleTabs`：当前模块内的功能页签，只对应本模块子页。
3. `PrototypePage`：逐页 React 实现，承载与 HTML 原型一致的信息架构、布局、表格、图表、右侧面板和动作。
4. `PageDataAdapter`：每个页面自己的数据适配器，负责把后端/BFF 响应转换成页面 ViewModel。

### 3.3 页面迁移策略

| 策略 | 结论 |
|---|---|
| 继续修 `NewUiModulePage` | 不采用。它适合作为临时占位，不适合全站原型落地。 |
| 直接嵌入 HTML 原型 | 不采用。视觉快，但无法接入真实数据、权限、交易和测试。 |
| 逐页 React 化新原型 | 采用。共享 shell/token/基础组件，页面主体逐页实现。 |

### 3.4 关键 UI 验收规则

1. 每个 preview HTML 对应一个 React route 或明确的模块 sub-route。
2. 首屏布局、页签文案、主表格/主图表/右侧操作面板必须与原型一致。
3. 页面交互必须保留：页签、分段筛选、候选选择、表格行点击、下单前检查、风控弹窗、抽屉、搜索、排序。
4. 所有页面都要有“等待真实数据”状态，不允许出现无说明的大空白。
5. P0 主链路页面必须能从候选一路追踪到方案、订单、风控判定和复盘。

## 4. 后端与接口改造原则

### 4.1 BFF 页面契约

在 API Gateway 后增加页面级聚合接口，优先满足新 UI 页面，而不是让页面直接拼装多个微服务。

建议路径：

| BFF 路径 | 用途 |
|---|---|
| `/api/v1/workbench/dashboard/:tab` | 智能看板 1.x |
| `/api/v1/workbench/open-decision/:tab` | 开盘决策 2.x |
| `/api/v1/workbench/screener/:tab` | 智能选股 3.x |
| `/api/v1/workbench/supply-chain/:tab` | 产业链 4.x |
| `/api/v1/workbench/prediction/:tab` | K线预测 5.x |
| `/api/v1/workbench/signals/:tab` | 交易信号 6.x |
| `/api/v1/workbench/trade/:tab` | 交易中心 7.x |
| `/api/v1/workbench/auto-trade/:tab` | 量化交易 8.x |
| `/api/v1/workbench/plans/:tab` | 方案管理 9.x |
| `/api/v1/workbench/risk/:tab` | 风控中心 10.x |
| `/api/v1/workbench/backtest/:tab` | 回测分析 11.x |
| `/api/v1/workbench/diagnosis/:tab` | 个股诊断 12.x |
| `/api/v1/workbench/admin/:tab` | 模型/数据/运行状态 13.x-16.x |

每个 BFF 响应统一包含：

```json
{
  "page": {},
  "data_domain": {
    "market": "public",
    "model": "public",
    "decision": "account",
    "trade": "account"
  },
  "context": {
    "tenant_id": "tenant-default",
    "owner_user_id": "1",
    "account_id": "paper-default",
    "role_view": "trader",
    "trade_mode": "paper",
    "broker_adapter": "paper"
  },
  "freshness": {},
  "lineage": {},
  "actions": []
}
```

### 4.2 服务复用与重构边界

| 服务 | 可复用 | 必须改造 |
|---|---|---|
| backend(auth) | JWT、RBAC、Tenant/Membership/BrokerAccount 雏形 | 租户成员、默认账户、套餐/权限、审计原因、跨租户约束 |
| api-gateway | 现有反向代理、服务健康别名 | 增加 BFF 聚合层、页面契约、统一错误/空状态 |
| screener-service | 多模式选股、产业链 API、候选契约测试 | CandidatePool 持久化、账户私有候选、P0 候选入方案 |
| prediction-service | Kronos 预测接口、历史/预测数据 | 预测总览与单股预测拆分、模型版本/置信度/关键价位/回测命中率 |
| signal-service | 信号、数据状态、同步状态 | 信号订阅、信号历史、风险扫描与 RiskVerdict 串联 |
| strategy-service | PlanStore 雏形、自动交易执行器 | Plan 持久化、方案生命周期、账户隔离、方案回测/下单联动 |
| trade-service | BrokerInterface、Mock/QMT、订单/风控 store 雏形 | 订单持久化、BrokerAccount 绑定、实盘闸门、审计日志、QMT gateway |
| backtest-service | 回测接口 | Plan-linked BacktestResult、交易拆解、失败样本、复盘报告 |
| training-service | 训练任务、MLflow | 发布闸门、模型版本状态、数据校验结果给前端 |
| diagnosis-service | 诊断引擎 | 与预测、信号、风险、个人笔记/报告联动 |

### 4.3 公共对象

五个公共对象是前后端、模型和交易的共同语言：

1. `DecisionContext`：一次决策输入、用户动作、模型版本和证据。
2. `Candidate`：候选标的，来源可为选股、信号、产业链、人工加入。
3. `Plan`：账户或租户内的交易方案。
4. `Order`：模拟或实盘订单。
5. `RiskVerdict`：候选、方案、订单、账户动作的风控判定。

字段细节以 `docs/design/New design/00 公共对象字段契约.md` 为准。

## 5. 模型与数据接口改造

### 5.1 模型服务统一输出

所有模型类接口必须返回：

- `model_id`
- `model_version`
- `run_id`
- `as_of`
- `data_freshness`
- `confidence`
- `feature_contributions`
- `fallback_reason`
- `lineage`

前端禁止只拿一个数值渲染。每个预测、信号、诊断结论都要能解释来源和时点。

### 5.2 数据服务要求

数据更新页面和所有业务页面都要消费统一 freshness：

| 字段 | 含义 |
|---|---|
| table | 数据表 |
| source | 数据源 |
| latest_trade_date | 最新交易日 |
| latest_update_at | 最近更新时间 |
| lag_minutes | 延迟 |
| row_count | 行数 |
| quality_status | ok / stale / missing / error |
| repair_action | 可触发修复动作 |

### 5.3 真实数据接入原则

1. 公共市场数据从 PostgreSQL/Tushare/cache 读取，SQLite 只作为兼容 fallback。
2. 账户私有数据必须进 PostgreSQL，不再用内存 store 作为正式路径。
3. 模型接口可以有 mock/fallback，但前端必须明确展示“等待真实模型 / 使用兜底逻辑”。

## 6. 交易与券商改造

### 6.1 交易安全基线

1. 默认模拟盘。
2. 实盘必须满足：账户绑定、券商通道在线、风险判定通过、二次确认、审计记录写入。
3. QMT/Xtquant 凭据、路径、账号配置不进入前端。
4. 云端部署时 QMT 通过 Broker Gateway/Windows 节点接入，主平台只调用 BrokerAdapter。

### 6.2 BrokerAdapter

统一接口：

- `connect`
- `account`
- `positions`
- `orders`
- `pre_check`
- `place_order`
- `cancel_order`
- `sync_fills`

默认实现：

| adapter | 用途 |
|---|---|
| `paper` | 默认模拟交易 |
| `xtquant_qmt` | QMT 实盘/仿真，必须通过 gateway |
| `broker_rest` | 后续其他券商 REST 接入 |

## 8. 验收标准

### 8.1 UI 验收

- 全部 preview 页面有对应 React route。
- 页面不再依赖 `NewUiModulePage` 作为正式主体。
- 页面首屏与新原型一致：布局、文案、页签、主视觉、右侧操作区、状态色。
- 关键交互保留并有测试：页签切换、筛选、选择候选、创建方案、下单前检查、风控结果、复盘跳转。

### 8.2 数据和接口验收

- 私有对象全部带 tenant/user/account scope。
- 公共对象和私有对象不混查。
- 页面 BFF 响应有 freshness、context、lineage、actions。
- API 无数据时返回结构化 empty/fallback，不让前端猜。

### 8.3 交易验收

- 模拟盘可从候选池完成：候选 -> 方案 -> 下单 -> 风控 -> 订单 -> 回测复盘。
- 实盘入口默认关闭，必须通过券商、账户、风控和审计。
- QMT 路径可配置但不自动实盘下单。

### 8.4 测试验收

- `cd frontend && npx vitest run`
- `cd frontend && npx tsc -b --noEmit`
- `cd frontend && npm run build`
- `cd backend && .venv/bin/pytest tests/ -v`
- changed service tests
- 浏览器 UAT 覆盖 `prototype-page-map.md` 中所有 route
