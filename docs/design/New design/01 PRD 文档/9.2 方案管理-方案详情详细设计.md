## 1. 页面定位

方案详情是方案管理的**核心查看与操作界面**，定位为 PlanManager 页面中的**右侧详情面板**（flex 60/40 布局中的 40%），也支持通过 URL 路由 `/plan/:id` 独立全屏访问。操盘手在此完成：标的配置审核 → 风控检查 → 启动/暂停/恢复/结算操作 → 订单执行跟踪。

**与 PlanManager 的关系**：
- PlanManager (60% 左 + 40% 右) → 右面板即 PlanDetailPanel
- 左侧 PlanList 点击方案卡片 → 右侧 PlanDetailPanel 切换内容
- 独立路由 `/plan/:id` → PlanDetailPage（全屏，带 ← 返回按钮）

## 4. 数据流

### 4.1 数据流全景

```
┌─────────────────────────────────────────────────────────────────────┐
│                      PlanDetail 数据流                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  初次加载:                                                          │
│    GET /api/v1/strategy/{id}  → { plan + orders + riskSummary }     │
│                                                                     │
│  轮询策略 (仅 running 状态):                                        │
│    setInterval 15s → GET /api/v1/strategy/{id}/live                 │
│    → { orders: OrderRecord[], stocks: PlanStock[] (含 realtimePnl) }│
│                                                                     │
│  操作流:                                                            │
│    [启动] POST /strategy/{id}/start → status='running' → 开始轮询   │
│    [暂停] POST /strategy/{id}/stop  → status='paused'  → 停止轮询   │
│    [恢复] POST /strategy/{id}/start → status='running' → 开始轮询   │
│    [结算] POST /strategy/{id}/settle → status='closed' → 停止轮询   │
│    [删除] DELETE /strategy/{id}  (仅draft)                          │
│                                                                     │
│  上下游数据:                                                         │
│    strategy-service (8003) ← 方案 + 订单 + 风控                      │
│    trade-service (8006)     ← 订单状态 + 成交价                       │
│    signal-service (8004)    ← 实时盈亏计算 (当前价)                   │
│    风控中心 (10.0)          → 止损逼近告警推送                       │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 关键交互时序

#### [启动] draft → running

```
1. PlanDetailPanel 发起 POST /strategy/{id}/start
2. strategy-service 校验:
   - stocks.length > 0
   - totalPosition > 0
   - riskPassed === true
3. DB: status='running', startedAt=now()
4. strategy-service → auto_trading_executor 创建执行器实例
5. auto_trading_executor → trade-service 逐笔发出买入订单
6. 响应 { status:'running', startedAt }
7. PlanDetailPanel:
   a. 更新 plan.status = 'running'
   b. 启动 15s 轮询定时器 usePlanPolling(planId)
   c. 显示 toast "方案已启动，正在自动下单"
```

#### 15s 轮询 (running 状态)

```
1. usePlanPolling(planId) 每 15s 触发
2. GET /strategy/{id}/live → { orders, stocks(含 currentPrice) }
3. 计算每只标的的 realtimePnl / stopLossDistance
4. 更新 StockAllocationTable 实时盈亏列
5. 更新 OrderList 订单状态
6. 检查 stopLossAlerts: 如有 <2% 的标的 → RiskSummary 红色闪烁
7. 更新 lastRefreshAt 时间戳
```

#### [结算] running/paused → closed

```
1. PlanDetailPanel 弹出确认 Modal
2. 确认后 POST /strategy/{id}/settle
3. strategy-service → trade-service 对所有未平仓持仓发出卖出订单
4. 等待全部成交或超时 (默认 60s)
5. DB: status='closed', settledAt=now(), finalPnl=...
6. 响应 { status:'closed', finalPnl, finalPnlAmount }
7. PlanDetailPanel:
   a. 停止轮询
   b. 更新 UI 为 closed 模式 (只读)
   c. 显示结算结果摘要
```

### 4.3 API 端点清单

| 方法 | 端点 | 用途 | 轮询 |
|---|---|---|---|
| `GET` | `/api/v1/strategy/{id}` | 获取方案详情(含订单/风险) | 否 |
| `GET` | `/api/v1/strategy/{id}/live` | 获取实时数据(订单状态+实时盈亏) | **是** (15s, running) |
| `POST` | `/api/v1/strategy/{id}/pause` | 暂停方案（进入 paused 状态） | 否 |
| `POST` | `/api/v1/strategy/{id}/resume` | 恢复方案（paused→running） | 否 |
| `POST` | `/api/v1/strategy/{id}/start` | 启动方案（draft→running） | 否 |
| `POST` | `/api/v1/strategy/{id}/settle` | 结算归档 | 否 |
| `PUT` | `/api/v1/strategy/{id}` | 编辑方案(draft) | 否 |
| `DELETE` | `/api/v1/strategy/{id}` | 删除方案(draft) | 否 |

## 6. 轮询 Hook

```typescript
// frontend/src/hooks/usePlanPolling.ts
function usePlanPolling(planId: string | null, status: PlanStatus, onData: (data: LiveData) => void) {
  const intervalRef = useRef<ReturnType<typeof setInterval> | null>(null)

  useEffect(() => {
    // 仅 running 状态启动轮询
    if (!planId || status !== 'running') {
      if (intervalRef.current) clearInterval(intervalRef.current)
      return
    }

    const poll = async () => {
      try {
        const res = await api.get(`/strategy/${planId}/live`)
        onData(res.data)
      } catch (e) {
        console.error('[PlanPolling] failed:', e)
      }
    }

    poll() // 立即执行一次
    intervalRef.current = setInterval(poll, 15000)

    return () => {
      if (intervalRef.current) clearInterval(intervalRef.current)
    }
  }, [planId, status])
}
```

## 平台化优化补充

> 继承自 `0.3 平台化云端多租户总体需求设计.md`、`0.4 平台化云端多券商架构设计.md`、`0.5 平台化详细方案设计.md`。

| 维度 | 设计要求 |
|---|---|
| 模块定位 | 方案管理：Plan 是私有交易意图承载对象，可授权共享但默认仅本人可见。 |
| 角色差异 | 操盘手保留专业工作台；个人投资者默认简化解释视图；系统管理员获得配置、审计和运行治理视图。 |
| 数据隔离 | 私有 Plan + 公共模型引用。所有私有对象必须写入 `tenantId / ownerUserId / accountId? / visibility / dataScope`。 |
| 云端部署 | API 必须从认证上下文恢复租户与用户身份，禁止前端传入越权租户；列表接口默认只返回当前身份可见数据。 |
| 券商/交易 | Plan 启动前必须绑定账户/模式。凡涉及资金、订单、策略启停的动作必须经过 `RiskGate` 并写入 append-only 审计。 |
| 原型要求 | 页面顶部展示角色视图、数据域、账户隔离、券商模式和云端就绪状态；不得把公共行情数据与私有交易数据混在同一区块而不标识。 |
