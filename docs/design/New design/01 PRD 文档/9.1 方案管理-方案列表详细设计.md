## 2. 数据结构

### 2.1 TypeScript 接口

```typescript
// ── KPI 指标 ────────────────────────────────────
interface PlanKpi {
  totalPosition: number          // 总仓位 %，如 73
  availableCash: number          // 可用资金，如 342580
  totalPnl: number               // 合计盈亏金额，如 12580
  totalPnlPct: number            // 合计盈亏 %
  activePlanCount: number        // 运行中方案数
  draftPlanCount: number         // 草稿方案数
}

// ── 方案摘要（列表用） ──────────────────────────
interface PlanSummary {
  id: string
  name: string                   // "龙头战法-开盘 A"
  status: PlanStatus             // 'draft' | 'running' | 'paused' | 'closed'
  stockCount: number             // 标的数量
  positionPct: number            // 总仓位 %
  positionTag?: string           // "建议仓位 35%"（draft 用）
  dailyPnl?: number              // 日盈亏 %
  dailyPnlAmount?: number        // 日盈亏金额
  stockChips: StockChipInfo[]    // 前 5 个标的摘要
  orderProgress?: OrderProgressInfo  // 订单进度（running 用）
  finalPnl?: number              // 最终收益 %（closed 用）
  finalPnlAmount?: number        // 最终收益金额（closed 用）
  createdAt: string              // ISO datetime
  settledAt?: string             // 结算时间（closed 用）
}

interface StockChipInfo {
  name: string                   // "宁德"
  allocationPct: number          // 15
}

interface OrderProgressInfo {
  filled: number                 // 已成交数
  total: number                  // 总订单数
}

// ── 方案卡片 Props ──────────────────────────────
interface PlanCardProps {
  plan: PlanSummary
  selected: boolean
  allowedActions: PlanAction[]   // 当前状态 + 角色允许的操作
  onSelect: (planId: string) => void
  onAction: (planId: string, action: PlanAction) => void
}

// ── 筛选状态 ────────────────────────────────────
type PlanFilter = 'all' | 'running' | 'draft' | 'closed'

interface FilterTabItem {
  key: PlanFilter
  label: string                  // "全部" / "运行中" / "草稿" / "已归档"
  count: number
  dotColor?: string              // running=绿 / draft=灰 / closed=暗灰
}

// ── PlanList 页面状态 ───────────────────────────
interface PlanListState {
  // 数据
  kpi: PlanKpi
  plans: PlanSummary[]
  planCounts: Record<PlanFilter, number>

  // UI
  filter: PlanFilter
  selectedPlanId: string | null
  loading: boolean
}
```

## 3. 数据流

### 3.1 初始加载

```
PlanList mount
│
├── 1. GET /api/v1/strategy/summary
│       → 返回 PlanKpi（总仓位 / 可用资金 / 合计盈亏 / 方案数）
│
├── 2. GET /api/v1/strategy?page=1&size=50
│       → 返回 PlanSummary[] + total + planCounts
│
├── 3. 渲染:
│       ├── KpiRow（4 张 KPI 卡）
│       ├── FilterTabs（含计数）
│       └── PlanCard × N（按状态分组）
│
└── 4. 启动轮询（如有 running 方案）
        └── setInterval(fetchKpi, 15000)
```

### 3.2 筛选切换

```
FilterTab click("running")
│
├── 1. setFilter("running")
│
├── 2. 本地过滤: plans.filter(p => p.status === 'running')
│       或 API: GET /api/v1/strategy?status=running
│
├── 3. UI 响应:
│       ├── FilterTab.active → "运行中"
│       ├── PlanCard 过滤显示（仅 running）
│       ├── 分组标题 → "运行中的方案"
│       └── 计数 badge 高亮
```

### 3.3 方案卡片点击

```
PlanCard click("plan-A")
│
├── 1. setSelectedPlanId("plan-A")
│       └── 卡片 .selected 高亮（蓝色左边框 + accent-dim 背景）
│
├── 2. PlanManagerContext.setSelectedPlan(plan-A full detail)
│
└── 3. PlanManager SubTabBar → 自动切换到 "📊 方案详情" Tab
        └── PlanDetail 组件接收 selectedPlan props 渲染详情
```

### 3.4 操作按钮 → 方案状态变更

```
[🚀 启动] click("plan-C") — draft → running
│
├── 1. Popconfirm "确认启动自动交易？"
│
├── 2. POST /api/v1/strategy/{plan-C}/start
│       → Response: { planId, status: 'running', startedAt }
│
├── 3. 本地状态更新（乐观更新）:
│       ├── plan.status = 'running'
│       ├── card 更新：状态圆点 → running 脉冲、操作按钮 → pause/settle
│       ├── planCounts.running++, planCounts.draft--
│       └── KPI 行 totalPosition 重新计算
│
└── 4. Toast "🚀 方案已启动！自动交易执行器正在下单⋯"
```

### 3.5 轮询流程

```
usePlanPolling(pollingPlanIds)
│
├── 每 15s:
│   ├── 1. 批量请求 kpi: GET /api/v1/strategy/summary
│   │       → 更新 KpiRow 4 张卡
│   │
│   └── 2. 对每个 running planId:
│           └── GET /api/v1/strategy/{planId}/orders
│               → 更新对应 PlanCard 的 OrderProgress
│                  （订单进度条 + "X/Y 已成交" 文字）
│
└── 清理: PlanList 卸载 → clearInterval
```

## 平台化优化补充

> 继承自 `0.3 平台化云端多租户总体需求设计.md`、`0.4 平台化云端多券商架构设计.md`、`0.5 平台化详细方案设计.md`。

| 维度 | 设计要求 |
|---|---|
| 模块定位 | 方案管理：Plan 是私有交易意图承载对象，可授权共享但默认仅本人可见。 |
| 角色差异 | 操盘手保留专业工作台；个人投资者默认简化解释视图；系统管理员获得配置、审计和运行治理视图。 |
| 数据隔离 | 私有 Plan + 公共模型引用。所有私有对象必须写入 `tenantId / ownerUserId / accountId? / visibility / dataScope`。 |
| 云端部署 | API 必须从认证上下文恢复租户与用户身份，禁止前端传入越权租户；列表接口默认只返回当前身份可见数据。 |
| 券商/交易 | Plan 启动前必须绑定账户/模式。凡涉及资金、订单、策略启停的动作必须经过 `RiskGate` 并写入 append-only 审计。 |
| 原型要求 | 页面顶部展示角色视图、数据域、账户隔离、券商模式和云端就绪状态；不得把公共行情数据与私有交易数据混在同一区块而不标识。 |
