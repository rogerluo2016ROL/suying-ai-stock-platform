## 1. 设计原则

1. 同一个系统，三种入口：操盘手工作台、个人投资者助理、管理员控制台。
2. 同一个能力，两种数据：公共市场/模型数据共享，私有方案/交易/账户数据隔离。
3. 同一个交易界面，多种执行：模拟盘、QMT 实盘、未来券商接口统一为 `BrokerAdapter`。
4. 同一个模型输出，必须可解释：模型版本、数据更新时间、适用范围、置信度和风险。
5. 所有资金动作不可绕过 `RiskGate` 和审计日志。

## 3. 公共对象扩展

P0 五个对象继续保留，并补平台字段：

```typescript
interface PlatformScoped {
  tenantId: string
  ownerUserId?: string
  accountId?: string
  visibility: 'private' | 'tenant_shared' | 'public'
  dataScope: 'public' | 'tenant' | 'user' | 'account'
}

interface DecisionContext extends PlatformScoped {
  contextId: string
  tradeDate: string
  roleView: 'trader' | 'investor' | 'admin'
  sourceModule: string
  dataFreshness: DataFreshness
}

interface Candidate extends PlatformScoped {
  candidateId: string
  code: string
  sources: CandidateSource[]
  publicScores: ModelScore[]
  privateNotes?: UserNote[]
}

interface Plan extends PlatformScoped {
  planId: string
  sourceCandidateIds: string[]
  accountBinding?: string
  lifecycle: 'draft' | 'ready' | 'running' | 'paused' | 'closed' | 'archived'
}

interface Order extends PlatformScoped {
  orderId: string
  brokerAdapter: string
  mode: 'paper' | 'live'
  auditId?: string
}

interface RiskVerdict extends PlatformScoped {
  verdictId: string
  scope: 'candidate' | 'plan' | 'order' | 'strategy' | 'account'
  result: 'pass' | 'warn' | 'reject' | 'manual_review'
}
```

## 4. 模块落地要求

| 模块 | 必须补充 |
|---|---|
| 智能看板 | 三角色首页切换；个人投资者默认自选解释 |
| 开盘决策 | Candidate 私有化；候选来源保留公共证据引用 |
| 智能选股 | 筛选参数私有保存；公共模型评分只读 |
| 产业链拆解 | 公共产业链图谱与私有研究笔记分离 |
| K线预测 | 公共预测快照 + 用户自定义预测任务 |
| 交易信号 | 公共信号规则 + 私有订阅状态 |
| 交易中心 | 账户绑定、交易模式、券商状态、审计链路 |
| 量化交易 | 策略实例绑定租户/账户；个人投资者默认不可自动实盘 |
| 方案管理 | Plan 私有，支持授权共享和复制 |
| 风控中心 | 全局规则、租户规则、账户判定结果分层 |
| 回测分析 | 私有回测结果；公共因子库；回测口径固定展示 |
| 个股诊断 | 公共诊断 + 私有备注/报告 |
| 模型训练 | 仅管理员/模型管理员；训练资源和模型输出隔离 |
| 模型注册 | 模型版本、灰度、回滚和线上标记 |
| 数据更新 | 公共数据质量；普通用户简化状态 |
| 运行状态 | 管理员全量服务，其他角色只看业务可用性 |

## 5. API 与后端规则

所有私有资源接口遵循：

```text
GET /resource
  -> auth 解析 user
  -> tenant context
  -> permission check
  -> data scope filter
  -> audit if cross-tenant/admin action
```

写接口必须：

- 接收或恢复 `DecisionContext`。
- 自动写 `tenantId/ownerUserId/accountId`。
- 资金动作先调用 RiskGate。
- 实盘动作写 audit before/after。
- 返回数据域状态，前端可展示公共/私有/混合。

## 8. Phase A 工程基线（已落地）

### 8.1 前端平台上下文

已新增 `PlatformScope` / `PlatformSession`，并在主布局中显示平台上下文横条：

- 角色视图：`trader` / `investor` / `admin`。
- 数据边界：`tenantId`、`ownerUserId`、`accountId`、`visibility`、`dataScope`。
- 交易模式：`paper` / `live`。
- 券商适配：`paper` / `xtquant_qmt` / `broker_rest`。
- 后端暂未返回租户/账户字段时，前端使用确定性默认值，避免页面空态。

### 8.2 API 平台请求头

前端 API 客户端已支持注入当前平台上下文，并对所有 axios API 请求附加：

```text
X-Tenant-Id
X-Trade-Account-Id
X-Data-Scope
```

这些 header 只作为请求边界输入，不作为权限事实。权限仍以后端 JWT、RBAC、租户上下文校验为准。

### 8.3 后端租户/账户上下文

后端新增 `PlatformContext` 与统一依赖：

- `get_platform_context`：从认证用户和请求头解析租户、账户、角色视图。
- `require_account_scope`：用于方案、下单、持仓、账户等必须绑定 `account_id` 的接口。
- 非管理员跨租户访问直接返回 403。
- 管理员可显式切换租户上下文，后续必须补审计日志。

### 8.4 只读券商账户契约

交易服务新增只读平台契约，不触碰真实下单逻辑：

- `BrokerAdapterCapability`：描述 paper、XtQuant QMT、REST 券商适配器能力。
- `BrokerAccountView`：描述账户可见性、交易模式、同步能力、资产快照和平台边界。
- `paper` 适配器不得声明为 `live` 实盘账户。
- `xtquant_qmt` 标记为需要本地 QMT 网关。

### 8.5 Phase B 前置条件

进入全面前后端/模型对接前，需要补齐：

- `Tenant` / `Membership` / `BrokerAccount` 持久化表和迁移。
- 服务间统一读取 `PlatformContext` 的适配层。
- Plan / Candidate / Order / RiskVerdict 持久化字段落库。
- RiskGate 与订单链路的强制串联。
- QMT 和其他券商接入的 tech-lead review、模拟盘 SIT、实盘灰度开关和审计日志。

## 9. Phase B1 持久化基线（已落地）

### 9.1 平台身份模型

后端新增三类持久化对象：

- `Tenant`：租户边界，使用 `slug` 作为前端和 API 可读的 `tenant_id`。
- `Membership`：用户与租户的成员关系，保留 `role_view` 和默认租户标记。
- `BrokerAccount`：交易账户绑定，记录 `adapter`、`trade_mode`、默认账户、交易开关和同步开关。

本阶段只建立账户可见性和权限边界，不执行券商下单。

### 9.2 认证画像字段

`/api/v1/auth/me`、登录和注册响应补充平台字段：

```text
tenant_id
tenant_name
default_trade_account_id
trade_mode
broker_adapter
```

后端在未加载持久化关系时返回确定性默认值：

- 管理员：`platform` / `平台运营` / 无默认交易账户。
- 普通用户与分析师：`tenant-default` / `默认租户` / `paper-u{userId}`。

### 9.3 前端兼容策略

前端 `AuthContext` 已将 auth payload 统一归一化，兼容：

- 后端 snake_case：`tenant_id`、`default_trade_account_id`。
- 旧前端 camelCase：`tenantId`、`defaultTradeAccountId`。

### 9.4 Phase B2 前置条件

下一步进入资源级隔离：

- 在 `get_user_by_id` / 登录查询中显式加载默认 `Membership` 和 `BrokerAccount`。
- 将 `get_platform_context` 接入 Plan、Candidate、Backtest、Order 读写接口。
- 给 Candidate / Plan / RiskVerdict / Order 增加 `tenant_id`、`owner_user_id`、`account_id`、`visibility`、`data_scope` 字段。
- 建立 append-only 审计日志和 RiskGate 强制链路后，再评估 QMT/其他券商实盘接入。

## 10. Phase B2 资源级隔离与联调基线（已落地）

### 10.1 默认平台资源初始化

后端启动时执行 `ensure_platform_defaults`：

- 创建 `platform` 和 `tenant-default` 两个基础租户。
- 管理员默认归属 `platform`，角色视图为 `admin`，不绑定默认交易账户。
- 普通用户、内部分析师、外部分析师默认归属 `tenant-default`。
- 非管理员用户自动绑定个人模拟账户 `paper-u{userId}`。

注册路径已同步接入默认资源初始化，确保首次注册响应、首次登录响应和 `/api/v1/auth/me` 都能返回同一个租户/账户上下文。

### 10.2 方案管理隔离

`strategy-service` 的 `Plan` 已补齐平台字段：

```text
tenant_id
owner_user_id
account_id
visibility
data_scope
```

方案创建、列表、详情、修改、删除、确认等接口会读取：

```text
X-Tenant-Id
X-Trade-Account-Id
X-Data-Scope
```

并按 `tenant_id + owner_user_id + account_id` 做账户级私有过滤。普通用户无法读取其他账户创建的私有方案。

### 10.3 交易账户只读视图

`trade-service` 的纸面账户查询已返回平台边界字段：

```text
tenant_id
owner_user_id
account_id
adapter
trade_mode
visibility
data_scope
```

本阶段只增强账户视图和前端上下文，不改动实盘下单、QMT 网关、撤单或执行器资金路径。

### 10.4 已验证链路

本阶段使用一组干净本地端口完成联调：

- auth：`http://127.0.0.1:9021`
- strategy：`http://127.0.0.1:8023`
- trade：`http://127.0.0.1:8026`
- frontend：`http://127.0.0.1:3010`

验证结论：

- 管理员登录返回 `tenant_id=platform`。
- 普通用户注册返回 `tenant_id=tenant-default` 与 `default_trade_account_id=paper-u{userId}`。
- 通过前端代理登录后，交易账户接口返回同一个 `paper-u{userId}`。
- 用户 A 创建的账户级私有方案，用户 B 列表查询返回空，未发生方案泄露。

下一步进入 Candidate / Order / RiskVerdict 与审计链路：

## 11. Phase B3-1 订单与风控判定契约（已落地）

### 11.1 下单请求上下文

`trade-service` 的 `POST /api/v1/trade/order` 继续兼容原有字段，并新增可选上下文字段：

```text
decision_context_id
candidate_id
plan_id
```

接口同时读取平台请求头：

```text
X-Tenant-Id
X-Trade-Account-Id
```

后端使用 JWT 用户和请求头恢复订单边界：

```text
tenant_id
owner_user_id
account_id
visibility=private
data_scope=account
```

### 11.2 统一 RiskVerdict

paper 和 live 下单现在都会执行 `pre_check`，并返回统一的 `risk_verdict`：

```text
verdict_id
tenant_id
owner_user_id
account_id
scope=order
result=pass | warn | reject
symbol
trade_mode
decision_context_id
candidate_id
plan_id
order_id
risk_check
```

对于 `reject`，接口返回 400，`detail.extra` 即为完整 `RiskVerdict`。对于通过订单，响应同时返回 `order_scope`、`risk_verdict` 和兼容旧前端的 `risk_check`。

### 11.3 审计增强

现有 append-only audit 记录继续复用，不新增迁移。本阶段增强 payload：

- `PLACE_ORDER`：写入 `order_scope`、`decision_context_id`、`candidate_id`、`plan_id`、`risk_verdict`。
- `RISK_REJECT`：拒绝订单也写审计，不再只依赖异常响应。

本阶段仍不改 QMT、实盘券商、撤单、执行器资金路径。

### 11.4 已验证链路

通过前端代理 `http://127.0.0.1:3010` 验证：

- paper 小额买单返回 200，`risk_verdict.result=pass`，包含 6 条风控检查。
- paper 超额买单返回 400，`error_code=RISK_REJECT`，`detail.extra.result=reject`，并保留 `tenant-default / paper-u105 / CTX-B3-REJECT`。

## 12. Phase B3-2 Candidate 快照契约（已落地）

### 12.1 候选池输出

`screener-service` 在 `_normalize_picks` 阶段为每条候选补充公共候选契约：

```text
candidate_id = CAND-{source_mode}-{code}
```

该字段只说明“公共模型/公共数据生成的候选结果”，不代表用户已保存为私有资产。

前端 `Screener.generatePlan` 会将候选字段透传给 `strategy-service` 的 `addPicks`。如果遇到旧缓存或旧服务返回没有 `candidate_id`，前端按相同规则兜底生成。

`strategy-service` 的 Plan picks 保留原始候选快照字段，不剥离：

```text
candidate_id
source_module
source_mode
visibility
data_scope
```

Plan 本身仍由 Phase B2 的 `tenant_id / owner_user_id / account_id` 控制可见性，因此公共候选保存进入方案后会成为账户级私有方案的一部分。

`AuthContext` 归一化 `broker_connect_config` 为 `brokerConnectConfig`。交易中心优先使用：

```text
user.brokerConnectConfig.account_id
```

如果后端没有返回该字段，则降级使用：

```text
user.defaultTradeAccountId || sandbox-qmt-001
```

### 25.4 边界

B9 不新增数据库迁移，不保存券商密码，不做真实账户托管。真实 QMT 账户接入仍需单独补：

```text
broker_accounts 扩展字段或独立 broker_credentials 表
密钥加密/托管策略
按 tenant/user/account 的权限隔离
实盘二次确认和审计
```

## 26. B10/B11 API Gateway 与前端 API Client 收口

### 26.1 目标

B10/B11 解决“前端页面与后端服务是否统一通过网关、是否稳定携带账号上下文”的底座问题。

统一链路：

```text
frontend api/client.ts
  -> /api/v1/*
  -> api-gateway:8080
  -> backend / screener / prediction / strategy / signal / alert / trade / backtest / training / diagnosis
```

### 26.2 网关路由矩阵

当前锁定的服务路由：

```text
/api/v1/auth       -> backend:9001
/api/v1/admin      -> backend:9001
/api/v1/screener   -> screener-service:8001
/api/v1/prediction -> prediction-service:8002
/api/v1/strategy   -> strategy-service:8003
/api/v1/signal     -> signal-service:8004
/api/v1/dashboard  -> signal-service:8004
/api/v1/data       -> signal-service:8004
/api/v1/alert      -> alert-service:8005
/api/v1/trade      -> trade-service:8006
/api/v1/backtest   -> backtest-service:8007
/api/v1/training   -> training-service:8008
/api/v1/diagnosis  -> diagnosis-service:8009
```

新增网关健康别名：

```text
/api/v1/trade/health -> trade-service /api/v1/health
```

同理适用于其他服务前缀，便于前端或运维统一按“服务名/health”探活。

### 26.3 前端 API Client

前端主 client 保持：

```text
baseURL=/api/v1
```

并统一注入：

```text
Authorization
X-Tenant-Id
X-Trade-Account-Id
X-Data-Scope
```

Gateway 自身健康检查是例外，使用 root path：

```text
GET /health
```

避免被错误拼成 `/api/v1/health`。
