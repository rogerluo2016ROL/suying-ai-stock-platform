> **Date**: 2026-06-27  
> **Owner**: product-lead

---

## 1. 设计目标

P0 主链路只解决一个问题：操盘手从多源候选标的中形成可执行方案，并在下单前、执行中、复盘后始终保留同一份决策上下文。

主链路固定为：

```text
候选池 -> 方案管理 -> 下单面板 -> 风控闸门 -> 回测复盘
```

本设计不新增一级菜单。它把现有 2.4、9.x、7.1、10.x、11.x 五组页面串成同一条链路，并定义五个公共对象：

```text
DecisionContext / Candidate / Plan / Order / RiskVerdict
```

## 3. 主链路拆解

### 3.1 候选池

目标：把竞价、信号、智能选股、自选、产业链等来源统一成 Candidate，并完成第一道风控。

入口：

- `2.4 candidate-pool-preview.html`
- `3.1 screener-workbench-preview.html`
- `4.2 chain-decompose-preview.html`
- `5.0 prediction-preview.html`
- `6.1 signal-overview-preview.html`

关键交互：

1. 用户勾选 3-5 只可用候选。
2. 右侧展示方案预览，不跳页。
3. 候选池风控先排除强制风险，再给警告项。
4. 点击“保存为手动方案”或“确认提交自动交易”时创建 Plan。

设计要求：

- 候选行必须展示来源、共识度、综合评分、Kronos 方向、风险状态。
- 被强制排除的 Candidate 不可勾选。
- 生成方案时必须写入 `DecisionContext.contextId`，后续页面全部沿用。

### 3.2 方案管理

目标：把 Candidate 组合升级为 Plan，成为交易执行前的唯一业务承载对象。

入口：

- `9.1 plan-list-preview.html`
- `9.2 plan-detail-preview.html`

关键交互：

1. 新建方案默认 `draft`。
2. `draft` 可编辑仓位、止损、止盈、执行方式。
3. 启动前必须请求方案级 RiskVerdict。
4. 手动下单时逐笔生成 Order 草稿并带入交易中心。
5. 自动交易时生成 Strategy/Executor，但仍以 Plan 作为业务主对象。

设计要求：

- Plan 详情必须显示来源 Candidate、目标仓位、止损止盈、风险摘要、订单进度和回测引用。
- 状态建议统一为 `draft | ready | running | paused | closed | archived`。
- 当前后端 `confirmed` 可映射为 `ready`，前端展示不直接暴露 `confirmed`。

### 3.3 下单面板

目标：把 PlanItem 转换为 Order，并在用户确认前展示价格、数量、金额、仓位和风控预检。

入口：

- `7.1 order-panel-preview.html`

关键交互：

1. 从方案详情点击“手动下单”进入，URL 只带 `contextId/planId/itemId/code`。
2. 页面恢复 DecisionContext，自动填入代码、建议价、建议仓位、止损止盈参考。
3. 用户可点击行情价/盘口价填入委托价。
4. 点击预检后展示 RiskVerdict，风险通过或警告确认后才可提交。

设计要求：

- Order 必须记录 `sourcePlanId`、`sourceCandidateId`、`contextId`。
- `price=0` 表示市价，但市价单需要大额确认。
- A 股数量必须为 100 股整数倍。

### 3.4 风控闸门

目标：RiskVerdict 不是一个页面结果，而是所有资金相关动作的统一闸门。

入口：

- `10.1 risk-overview-preview.html`
- `10.2 position-risk-preview.html`
- `10.3 strategy-risk-preview.html`
- `7.1 order-panel-preview.html`
- `9.2 plan-detail-preview.html`

闸门分层：

| 层级 | 触发点 | 判定对象 | 必须输出 |
|---|---|---|---|
| 候选池风控 | 生成方案前 | Candidate[] | 排除/警告/通过 |
| 方案风控 | 启动/保存执行方案前 | Plan | 总仓位、单票集中、止损覆盖、熔断状态 |
| 审单风控 | 提交 Order 前 | Order | 资金、持仓、涨跌停、仓位、单笔上限、大额确认 |
| 执行风控 | 自动策略运行中 | Plan + Order[] | 暂停、恢复、强制卖出、熔断 |
| 复盘风控 | 方案关闭后 | Plan + Backtest | 风控命中、拒绝原因、规则有效性 |

设计要求：

- RiskVerdict 只允许四种最终结论：`pass | warn | reject | manual_review`。
- `reject` 禁止继续下单。
- `warn` 必须记录用户确认人和确认时间。
- `manual_review` 进入风控中心事件审计，不自动放行。

### 3.5 回测复盘

目标：对已形成或已执行的 Plan 做历史验证和执行后复盘。

入口：

- `11.1 backtest-run-preview.html`
- `11.3 backtest-trades-preview.html`
- `9.4 settlement-report-preview.html`

关键交互：

1. 从 Plan 详情点击“回测复盘”进入。
2. 回测参数默认继承 Plan 的候选、仓位、止损、止盈、持有周期。
3. 展示权益曲线、回撤、胜率、交易明细和与实际订单的偏差。
4. 复盘结果写回 Plan 的 `backtestRef`。

设计要求：

- 回测页必须显示数据口径：基准、手续费、滑点、样本内/样本外、数据更新时间。
- 结论必须区分“历史回测表现”和“真实执行表现”，不能混在一个收益数字里。

## 5. 页面原型优化要求

### 5.1 候选池原型

必须显示：

- DecisionContext 摘要：`contextId/tradeDate/sourceModule/dataFreshness`。
- Candidate 数量：原始输入、去重、可用、排除、已选。
- 方案预览中显示 Plan 编号、执行模式、RiskVerdict 状态。
- 提交后明确去向：自动交易到执行监控，手动方案到方案详情/下单面板。

### 5.2 方案管理原型

必须显示：

- Plan 状态机。
- Plan 与 Candidate 的来源关系。
- 风控摘要与订单进度。
- 手动下单 CTA 必须带 `contextId/planId/itemId/code`。

### 5.3 下单面板原型

必须显示：

- 方案带入标签中展示 `planId/itemId/contextId`。
- 下单表单中展示 `Order` 预览字段。
- 风控预检结果采用 RiskVerdict 命名，不再只是“6项检查”。

### 5.4 风控原型

必须显示：

- 不同 scope 的 RiskVerdict 队列。
- `pass/warn/reject/manual_review` 四种状态。
- 告警点击后能说明回到哪个对象和页面处理。

### 5.5 回测复盘原型

必须显示：

- 从 Plan 带入的默认参数。
- Backtest 结果写回 Plan 的引用。
- 区分历史回测收益和真实执行收益。

## 平台化优化补充

> 继承自 `0.3 平台化云端多租户总体需求设计.md`、`0.4 平台化云端多券商架构设计.md`、`0.5 平台化详细方案设计.md`。

| 维度 | 设计要求 |
|---|---|
| 模块定位 | 总体设计：作为平台级基线，被所有角色和模块继承。 |
| 角色差异 | 操盘手保留专业工作台；个人投资者默认简化解释视图；系统管理员获得配置、审计和运行治理视图。 |
| 数据隔离 | 公共/私有/审计数据分层。所有私有对象必须写入 `tenantId / ownerUserId / accountId? / visibility / dataScope`。 |
| 云端部署 | API 必须从认证上下文恢复租户与用户身份，禁止前端传入越权租户；列表接口默认只返回当前身份可见数据。 |
| 券商/交易 | 按模块决定是否触达券商。凡涉及资金、订单、策略启停的动作必须经过 `RiskGate` 并写入 append-only 审计。 |
| 原型要求 | 页面顶部展示角色视图、数据域、账户隔离、券商模式和云端就绪状态；不得把公共行情数据与私有交易数据混在同一区块而不标识。 |
