## 1. 页面定位

因子分析是智能选股的**因子研究工具**，定位为"因子显微镜"——用户选择时间窗口后，回答三个核心问题：
- **哪个因子有效？** → IC 柱状图
- **有效但稳定吗？** → ICIR 统计表
- **哪些因子冗余？** → 相关性热力图

与模型对比的区别：

| | 模型对比 (3.2) | 因子分析 (3.3) |
|---|---|---|
| **比较什么** | 模型 vs 模型 | 因子 vs 因子 |
| **输出** | 共识股票 | IC/ICIR/相关性/分层收益 |
| **目的** | 选股决策 | 权重校准 + 模型优化 |
| **使用者** | 操盘手 + 个人投资者 | 量化研究员 + 高级操盘手 |

阅读路径：
- 顶部 IC 柱状图：一眼看到最有效的因子
- 中部热力图：理解因子之间的关联结构
- 下部分层收益表：验证因子是否有单调的收益区分能力
- 右侧 ICIR 统计表：量化因子的稳定性和显著性
- 点击某个因子 → 分层表切换到该因子

### 1.1 应用逻辑

```
Step 1: 选择模型 → 确定要分析哪些因子
  毕师傅 V13 → 6 个因子 (OBV/WR/量比/强动态/涨幅/波动率)

Step 2: 选择时间窗口 → 看不同周期的因子表现
  近30天: 短期有效因子
  近60天: 中期稳定因子 (推荐默认)
  近120天: 长期稳健因子

Step 3: 阅读 IC 柱状图 → 识别有效和无效因子
  ████████ OBV趋势 IC=+0.062 ICIR=1.52 ← 有效且稳定 ✅
  ██████   WR超卖  IC=+0.038 ICIR=0.72 ← 有效但不稳定
  ████     强动态  IC=+0.015 ICIR=0.31 ← 近期失效 ❌

Step 4: 检查相关性 → 去除冗余因子
  热力图中 OBV↔量比 r=0.78 (深红) ← 高度相关，两个留一个

Step 5: 验证分层 → 确认因子有区分能力
  D1(最低) = -3.2% → D10(最高) = +7.8% = 多空spread +11.0%
  单调递增 ✓ → 因子有效

Step 6: 调参决策
  去掉: ICIR < 0.5 的因子
  合并: 相关性 > 0.7 的因子对
  加权: 按 abs(ICIR) 重新分配因子权重
```

### 5.3 转换为 Heatmap 数据

```typescript
function toHeatmapData(factors: string[], matrix: number[][]): Array<{value: number[]}> {
  const data: Array<{value: number[]}> = []
  for (let i = 0; i < factors.length; i++) {
    for (let j = 0; j < factors.length; j++) {
      data.push({ value: [j, i, parseFloat(matrix[i][j].toFixed(2))] })
    }
  }
  return data
}
```

## 6. 核心数据结构

### 6.1 页面状态

```typescript
interface FactorAnalysisState {
  // 时间窗口
  days: number                    // 7 | 30 | 60 | 120

  // IC 数据
  icData: FactorIC[] | null

  // 相关性数据
  correlationData: CorrelationData | null

  // 分层收益
  selectedFactor: FactorIC | null
  decileData: FactorDecile[] | null

  // 行业暴露
  industryExposure: IndustryExposure[] | null

  // UI
  loading: boolean
  error: string | null
}

interface FactorIC {
  factorKey: string
  factorName: string
  category: string
  icMean: number
  icStd: number
  icir: number
  tStat: number
}

interface CorrelationData {
  factors: string[]
  matrix: number[][]
}

interface FactorDecile {
  decile: number
  label: string
  cumReturn: number
  avgReturn: number
}

interface IndustryExposure {
  industry: string
  exposure: number           // 该行业在该因子上的均值
  rank: string               // "偏高" / "偏低" / "中性"
}
```

### 6.2 预计算缓存表（factor_ic_cache）

IC/相关性/分层收益由 training-service 的 APScheduler 定时预计算后写入 PG，本页面只读缓存（API P95 ≤ 500ms）。缓存表结构：

```sql
CREATE TABLE IF NOT EXISTS factor_ic_cache (
    id BIGSERIAL PRIMARY KEY,
    factor_key VARCHAR(60) NOT NULL,        -- 因子标识，如 obv_trend
    days INT NOT NULL,                      -- 分析窗口：7/30/60/120
    ic DOUBLE PRECISION NOT NULL,           -- IC 均值
    icir DOUBLE PRECISION NOT NULL,         -- ICIR
    t_stat DOUBLE PRECISION,                -- t 统计量
    calc_date DATE NOT NULL,                -- 计算日期（交易日）
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_factor_ic_cache UNIQUE(factor_key, days, calc_date)
);
```

> **口径对齐**：training-service 已存在 `GET /api/v1/training/factors/ic`（`services/training-service/app/routes.py:1103`，响应含 `ic_mean/ic_std/icir_mean/direction/rolling`）。本表字段（ic/icir/t_stat）与该端点同一计算口径，实现时复用其 IC 计算逻辑；相关性矩阵与分层收益缓存可复用同表扩展（`factor_key` 存因子对 / `D1-D10` 分层键）或另建同构表，**待实现时验证**。
>
> 行业暴露数据由预计算任务按 `stocks.industry` 分组聚合因子均值生成，同样落缓存（表结构随实现补充），前端仅通过 §7 的四个 GET 端点读取。

## 7. 数据流与 API 调用

```
页面加载 (useEffect [days, selectedFactor])
  │
  ├── Promise.all([
  │     GET /api/v1/screener/factors/ic?days={days}
  │     GET /api/v1/screener/factors/correlation?days={days}
  │   ])
  │   │
  │   ├── icData → IC 柱状图 + ICIR 统计表
  │   │   └── setState({ selectedFactor: icData[0] })  // 默认选第一个
  │   │
  │   └── correlationData → 热力图
  │
  ├── selectedFactor 变化 →
  │   ├── GET /api/v1/screener/factors/decile-return?days={days}&factor={factorKey}
  │   │   └── decileData → 分层收益表
  │   │
  │   └── GET /api/v1/screener/factors/industry-exposure?days={days}&factor={factorKey}
  │       └── industryExposure → 行业暴露表
  │
  └── days 变化 → 重新触发所有请求

点击 IC 柱状图中的某根柱子
  └── setState({ selectedFactor: clickedFactor })
      └── 触发 decile-return + industry-exposure 重新请求
```

### 性能优化策略

| 策略 | 说明 |
|---|---|
| 后端预计算 | IC/相关性/分层收益均由定时任务预计算写入 PG 缓存表（`factor_ic_cache`，见 §6.2） |
| 前端请求合并 | 并行请求 IC + 相关性 |
| 条件请求 | 分层收益和行业暴露仅在 factor 变化时请求 |
| 热力图优化 | 因子数 ≤ 12，渲染量极小 |

## 平台化优化补充

> 继承自 `0.3 平台化云端多租户总体需求设计.md`、`0.4 平台化云端多券商架构设计.md`、`0.5 平台化详细方案设计.md`。

| 维度 | 设计要求 |
|---|---|
| 模块定位 | 智能选股：公共模型能力与用户私有筛选条件分离，结果可保存到个人候选池。 |
| 角色差异 | 操盘手保留专业工作台；个人投资者默认简化解释视图；系统管理员获得配置、审计和运行治理视图。 |
| 数据隔离 | 公共模型评分 + 私有筛选参数。所有私有对象必须写入 `tenantId / ownerUserId / accountId? / visibility / dataScope`。 |
| 云端部署 | API 必须从认证上下文恢复租户与用户身份，禁止前端传入越权租户；列表接口默认只返回当前身份可见数据。 |
| 券商/交易 | 不直接下单，只生成候选/方案。凡涉及资金、订单、策略启停的动作必须经过 `RiskGate` 并写入 append-only 审计。 |
| 原型要求 | 页面顶部展示角色视图、数据域、账户隔离、券商模式和云端就绪状态；不得把公共行情数据与私有交易数据混在同一区块而不标识。 |
