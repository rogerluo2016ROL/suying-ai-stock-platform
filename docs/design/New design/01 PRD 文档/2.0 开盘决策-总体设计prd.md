# PRD — 开盘决策·总体设计

- **Date**: 2026-06-26
- **Owner**: product-lead
- **Status**: Draft
- **Estimated effort tier**: Large（重构信息架构 + 3 个新 Tab + 2 个增强 Tab + 跨模块联动）

## 1. Background

速赢AI 现有功能按"业务域"组织（选股/预测/信号/交易），但操盘手的实际工作流是按**时间**组织的：

```
盘前(9:00) → 竞价(9:25) → 开盘(9:30) → 盘中(10:00-15:00) → 盘后(15:00+)
   判断方向      锁定板块      确认标的      执行+监控          复盘+选股
```

当前信息架构无法支撑这个流程——用户需要在 5-6 个菜单之间跳转才能完成一次完整的开盘决策。

**核心洞察**：开盘决策不是功能的集合，而是**时间驱动的工作流**。每个阶段回答一个问题，每个问题过滤一批候选。

## 2. Goal & Non-Goals

**目标**：

- 新增"开盘决策"一级菜单，内含 5 个二级功能，按时间顺序排列
- 操盘手在开盘 30 分钟内（9:00-9:30）完成从"判断方向"到"锁定标的"的完整链路
- KPI：从打开页面到生成候选池 ≤ 3 分钟（含竞价数据加载）

**Non-Goals**：

- 不替代"智能选股"（盘后选股仍为独立菜单）
- 不替代"风控中心"（风控跨所有阶段，保持独立）
- 不替代"交易中心"（下单操作保持独立，开盘决策只做"候选池→方案"）
- 不在开盘决策中创建/编辑自动交易策略（策略管理仍由量化交易页面负责）

## 4. 工作流设计

### 4.1 时间-问题-信息-决策 映射表

```
阶段             时间        回答的问题          看的信息              做的决策
──────────────────────────────────────────────────────────────────────────
P1 盘前准备    09:00-09:25  昨晚发生了什么？    隔夜新闻+公告+外盘   判断是否有重大利空
                            昨天市场怎么样？    昨日涨跌/涨停/板块   确认市场惯性方向
                            候选池准备好了吗？  昨日选股结果+自选    预加载今日候选池
                            今天能不能做？      情绪指数+熔断器状态   进攻/防御/观望
                            做什么方向？        竞价预告+板块热度     预判方向，等竞价确认

P2 竞价分析    09:25-09:27  哪些在抢筹？        抢筹TOP10+四维雷达   初筛10-15只
                            有没有选债机会？    概念选债+溢价率       转债候选

P3 信号扫描    09:27-09:29  哪只有信号确认？    信号矩阵(锁定板块)   压缩到5-8只
                            信号+预测一致吗？  Kronos预测+六维评分   排除预测相悖的

P4 候选池      09:29-09:30  候选质量够吗？      多源共识排序          最终3-5只
                             风险排除完了吗？    审计/公告/ST 检查     一票否决
                             能直接方案吗？      止损位/目标位/仓位    预览方案→自动交易/手动

P5 执行监控    09:30-15:00  执行了没有？        订单状态+成交回报     撤单/改单/补单
                             持仓安全吗？        止损逼近+浮盈亏       加减仓/止损
                             方案在哪？          今日方案（自动/手动） 启动/下单/删除
```

### 4.2 跨 Tab 数据流

```
市场情绪 ──情绪等级──→ 决策总览(KPI)
                     决策总览 ──"进攻日"──→ 竞价分析(筛选偏好偏多)
                     
竞价分析 ──选中板块──→ 信号扫描(验证列表)
          ──picks────→ 候选池(输入源)
         
信号扫描 ──确认信号──→ 候选池(交叉验证)
         
候选池   ──生成方案──→ 候选池内预览方案
          ──自动交易──→ strategy-service (创建策略+启动执行器)
            │               └→ trade-service (风控闸门→创建订单)
            │
          ──手动方案──→ strategy-service (保存方案)
            │               └→ 交易中心 (用户手动下单)
            │
          ──仅保存────→ strategy-service (保存草稿)

候选池+交易中心 ──订单──→ 执行监控(订单+持仓+策略)
              ──方案──→ 执行监控(今日方案面板)

执行监控 ──止损逼近──→ 风控中心(告警)
```

### 4.3 方案生成→提交流程（候选池内完成）

```
候选池勾选 3-5 只 → [生成方案]
  │
  ▼ 候选池右侧切换为"方案预览"
  Step 1: 系统自动计算（止损位/目标位/仓位分配）
  Step 2: 用户审查调整（仓位拖动/止损止盈选择）
  Step 3: 风控预检（总仓位/单票上限/熔断器）
  │
  ├── [确认提交→自动交易]
  │     POST /strategy/generate-and-start
  │     → 创建策略 + 启动执行器 → 自动逐笔下单
  │     → 订单 → 执行监控 Tab + 交易中心
  │
  ├── [保存为手动方案]
  │     POST /strategy/generate
  │     → 保存方案（不启动，不生成订单）
  │     → 方案 → 执行监控"今日方案"面板
  │     → 用户到交易中心手动逐笔下单
  │
  └── [仅保存]
        → 保存为草稿，留在候选池

## 5. 五个二级功能定义

### 5.1 决策总览 — 聚合仪表盘

- **职责**：5 个阶段的 KPI 浓缩到一屏。只读，不操作
- **数据来源**：聚合市场情绪、竞价概况、信号密度、自选触发、熔断器状态
- **详见**：`2.1 开盘决策-决策总览prd.md`

### 5.2 竞价分析 — 发现方向

- **职责**：竞价意图 + 龙头竞价选股 + 竞价概念选债，三合一
- **数据来源**：竞价意图(已有PRD 1.2) + leader_auction V4.3 + cb_auction V1.0
- **与 1.2 的关系**：`1.2 智能看板-竞价意图prd.md` 定义的竞价意图看板功能完整移入竞价分析 Tab，并增加选股/选债结果展示
- **详见**：`2.2 开盘决策-竞价分析prd.md`

### 5.3 信号扫描 — 确认标的

- **职责**：信号矩阵(锁定竞价选中的板块) + 信号详情 + Kronos 预测交叉验证
- **数据来源**：信号总览(已有PRD 1.3) + signal-service 六维评分 + Kronos 预测
- **与 1.3 的关系**：`1.3 智能看板-信号总览prd.md` 定义的信号矩阵功能移入信号扫描 Tab，并增加板块锁定筛选 + Kronos 预测叠加
- **详见**：`2.3 开盘决策-信号扫描prd.md`

### 5.4 候选池 — 融合决策

- **职责**：多源 picks 融合 + 共识排序 + 交叉验证 + 一键生成方案
- **数据来源**：竞价分析 picks + 信号扫描 picks + 智能选股 picks + 自选共振
- **新建能力**
- **详见**：`2.4 开盘决策-候选池prd.md`

### 5.5 执行监控 — 跟踪执行

- **职责**：订单状态 + 持仓盈亏 + 止损逼近 + 策略运行状态
- **数据来源**：trade-service + broker positions + auto_trading status
- **新建能力**
- **详见**：`2.5 开盘决策-执行监控prd.md`

## 6. 与现有系统的关系

| 现有模块 | 开盘决策上线后的变化 |
|---|---|
| **AI 智能看板** (1.1-1.5) | 缩为 3 个 Tab（市场情绪/自选跟踪/运行状态）。竞价意图(1.2)和信号总览(1.3)移入开盘决策 |
| **智能选股** (独立菜单) | 保留。盘后选股（毕师傅/秋神盘后/匪爷/长线等）不变。竞选股/选债（leader_auction/cb_auction）集成到竞价分析 |
| **风控中心** | 保留。执行监控 Tab 中展示止损逼近摘要，详情仍跳转风控中心 |
| **交易中心** | 保留。候选池"生成方案"后跳转交易中心下单 |
| **方案管理** | 保留。候选池"生成方案"调用方案管理 |

## 7. 技术约束

- 前端框架：React 18 + TypeScript 5.6 + Ant Design 5.22 + ECharts 5.5
- 页面实现：`frontend/src/pages/OpeningDecision.tsx` 作为主页面，内含 `<Tabs>` 切换 5 个 Tab
- 路由：`/opening-decision`（独立路由），左侧菜单"📈 开盘决策"为一级项
- 时段感知：前端根据当前时间自动切换默认 Tab
- 跨 Tab 联动：通过 React Context（`OpeningDecisionContext`）共享选中板块/股票/候选池
- 设计系统：遵循 `docs/design/new front/design-spec.md` 及 `design-tokens.css`
- 不引入新 npm/Python 依赖

## 平台化优化补充

> 继承自 `0.3 平台化云端多租户总体需求设计.md`、`0.4 平台化云端多券商架构设计.md`、`0.5 平台化详细方案设计.md`。

| 维度 | 设计要求 |
|---|---|
| 模块定位 | 开盘决策：操盘手默认入口，输出私有 Candidate 与 DecisionContext。 |
| 角色差异 | 操盘手保留专业工作台；个人投资者默认简化解释视图；系统管理员获得配置、审计和运行治理视图。 |
| 数据隔离 | 公共竞价/行情 + 私有候选池。所有私有对象必须写入 `tenantId / ownerUserId / accountId? / visibility / dataScope`。 |
| 云端部署 | API 必须从认证上下文恢复租户与用户身份，禁止前端传入越权租户；列表接口默认只返回当前身份可见数据。 |
| 券商/交易 | 实盘前必须进入方案与风控。凡涉及资金、订单、策略启停的动作必须经过 `RiskGate` 并写入 append-only 审计。 |
| 原型要求 | 页面顶部展示角色视图、数据域、账户隔离、券商模式和云端就绪状态；不得把公共行情数据与私有交易数据混在同一区块而不标识。 |
