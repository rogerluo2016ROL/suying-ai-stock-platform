## 3. 核心数据结构

```typescript
type OrderStatus = 'pending' | 'filled' | 'partial' | 'cancelled' | 'rejected'
type OrderFilter = 'all' | 'pending' | 'filled' | 'cancelled'

interface OrderRecord {
  id: string
  orderTime: string
  tsCode: string
  name: string
  side: 'buy' | 'sell'
  orderType: 'limit' | 'market'
  price: number
  qty: number
  amount: number
  filledQty: number
  status: OrderStatus
  modifiable: boolean
  cancellable: boolean
}

interface ModifyOrderRequest {
  price?: number
  qty?: number
}
```

### 3.1 筛选逻辑

```typescript
function filterOrders(orders: OrderRecord[], filter: OrderFilter): OrderRecord[] {
  switch (filter) {
    case 'pending': return orders.filter(o => o.status === 'pending' || o.status === 'partial')
    case 'filled': return orders.filter(o => o.status === 'filled')
    case 'cancelled': return orders.filter(o => o.status === 'cancelled' || o.status === 'rejected')
    default: return orders
  }
}

function getFilterCounts(orders: OrderRecord[]) {
  return {
    all: orders.length,
    pending: orders.filter(o => o.status === 'pending' || o.status === 'partial').length,
    filled: orders.filter(o => o.status === 'filled').length,
    cancelled: orders.filter(o => o.status === 'cancelled' || o.status === 'rejected').length,
  }
}
```

## 4. 数据流

### 4.1 订单轮询

```
OrderManagement mount
  │
  ├── GET /trade/orders?date=today
  │   └── 返回 orders[]
  │
  ├── 计算 counts (all/pending/filled/cancelled)
  │
  └── 轮询: setInterval(30s) → GET /trade/orders?date=today
```

### 4.2 改单流程

```
1. 点击待成交行 [✏️改单]
2. 打开 ModifyOrderModal, 预填当前 price/qty
3. 用户修改价格和/或数量
4. 点击 [确认修改]
5. PUT /trade/order/{id} { price, qty }
6. 成功: toast "✅ 订单 #ORD-003 已修改" + 刷新列表
7. 失败: toast "❌ 改单失败: ..." + 不关闭弹窗
```

### 4.3 撤单流程

```
1. 点击 [✖️撤单]
2. confirm("确认撤销订单 #ORD-003？")
3. DELETE /trade/order/{id}
4. 成功: toast "✅ 订单已撤销" + 刷新列表
5. 失败: toast "❌ 撤单失败: ..."
```

### 4.4 全部撤单流程

```
1. 点击 [❌ 全部撤单]
2. confirm(`确认撤销全部 ${pendingCount} 笔待成交订单？`)
3. DELETE /trade/orders (批量)
4. 成功: toast "✅ 已撤销 N 笔订单" + 刷新列表
```

## 平台化优化补充

> 继承自 `0.3 平台化云端多租户总体需求设计.md`、`0.4 平台化云端多券商架构设计.md`、`0.5 平台化详细方案设计.md`。

| 维度 | 设计要求 |
|---|---|
| 模块定位 | 交易中心：账户、订单、持仓、成交全部按 tenant/account/user 隔离。 |
| 角色差异 | 操盘手保留专业工作台；个人投资者默认简化解释视图；系统管理员获得配置、审计和运行治理视图。 |
| 数据隔离 | 强私有交易数据。所有私有对象必须写入 `tenantId / ownerUserId / accountId? / visibility / dataScope`。 |
| 云端部署 | API 必须从认证上下文恢复租户与用户身份，禁止前端传入越权租户；列表接口默认只返回当前身份可见数据。 |
| 券商/交易 | paper/QMT/多券商统一 BrokerAdapter。凡涉及资金、订单、策略启停的动作必须经过 `RiskGate` 并写入 append-only 审计。 |
| 原型要求 | 页面顶部展示角色视图、数据域、账户隔离、券商模式和云端就绪状态；不得把公共行情数据与私有交易数据混在同一区块而不标识。 |
