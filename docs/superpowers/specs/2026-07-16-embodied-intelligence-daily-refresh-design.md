# 具身智能复杂产业链每日刷新与证据变动推送设计

## 1. 背景与目标

现有具身智能复杂产业链已具备 L1–L8 层级、公司业务标签、证据事件和候选映射能力，但存在三个核心问题：

1. 数据与股票映射需要人工触发，不能每日持续更新；
2. 映射状态与证据审核状态口径不一致，难以追踪映射为何升级或降级；
3. 缺少前后版本对比和变动推送，无法及时识别客户、定点、订单、量产和收入等重要证据链变化。

本设计的目标是建立一套可追溯、可重跑、可审计的具身智能产业链刷新流程：

- 每天北京时间 19:30 自动增量刷新；
- 每周日 20:30 执行全量一致性审计；
- 按证据规则补充并更新公司—节点映射；
- 识别新增、增强、升级、降级、节点调整和失效；
- 对重要变动排序后推送到“AI 投研分析”、“AI 投研测试”和“一起减肥吧”三个飞书群；
- 没有 P0–P2 级变动时不发送消息，但保留运行日志。

## 2. 范围与非目标

### 2.1 范围

- 具身智能复杂产业链 `embodied_intelligence`；
- L1–L8 层级节点、八个横向维度和公司业务标签；
- 公告、定期报告、监管问询、官方信息、交易所互动问答、研报、主营业务和行情等已有项目数据源；
- 核心节点 Top3 龙头映射及其变动；
- 三个飞书群的变动推送、送达确认和失败重试。

### 2.2 非目标

- 不将概念标签或关键词命中直接转换为投资推荐；
- 不使用股价涨跌直接提升产业映射等级；
- 不因某个数据源当日失败而自动降级已有映射；
- 不对其他产业链进行全量重构；
- 不修改当前工作树中与本任务无关的改动。

## 3. 总体方案

采用“每日增量刷新＋每周全量审计”方案。每日任务处理上次成功游标之后新增或修改的数据，每周任务只识别历史偏差和数据不一致，不自动覆盖正式映射。

```text
每日 19:30 触发
  -> 数据新鲜度检查
  -> 增量读取数据源
  -> 证据抽取、标准化、去重与冲突检测
  -> 更新 L1–L8 节点与公司映射
  -> 八层覆盖和数据质量审计
  -> 核心节点 Top3 重排
  -> 与上一次成功快照比较
  -> 变动重要性评分
  -> 有 P0–P2 变动：推送三个飞书群并记录 message_id
  -> 无 P0–P2 变动：不推送，只记录成功日志
```

## 4. 组件边界

实现拆分为五个职责单一的模块和一个统一入口：

| 组件 | 职责 | 输入 | 输出 |
|---|---|---|---|
| `refresh_embodied_sources` | 检查新鲜度并增量读取数据 | 上次成功游标 | 分数据源的原始增量记录 |
| `extract_embodied_evidence` | 抽取、标准化、去重、冲突检测 | 原始增量记录 | 标准证据事件 |
| `rebuild_embodied_mappings` | 执行映射新增、增强、升级、降级和失效 | 标准证据事件 | 映射当前状态与变更历史 |
| `audit_embodied_chain` | 审计 L1–L8 覆盖、重复节点、冲突映射和 Top3 | 更新后数据 | 审计报告与排名快照 |
| `publish_embodied_changes` | 生成变动摘要、推送、重试并核验送达 | 前后快照差异 | 三群推送结果与 `message_id` |
| `run_embodied_daily_refresh` | 编排、幂等锁、事务边界和运行归档 | 调度参数 | 批次结果 |

## 5. 证据来源与自动升级

### 5.1 来源分级

| 级别 | 来源 | 用途 |
|---|---|---|
| S | 公司公告、定期报告、监管问询回复 | 可支撑自动升级 |
| A | 公司官网、官方公众号、投资者关系活动记录 | 可在规则满足时支撑升级 |
| B | 交易所互动问答、政府或客户官方信息 | 加强证据链 |
| C | 正规研报、权威媒体采访 | 辅助证据 |
| D | 新闻转载、自媒体、概念标签和关键词命中 | 只生成候选线索 |

### 5.2 状态规则

- 新映射统一以 `candidate/pending_review` 入库；
- 一条 S 级明确证据，或两条相互独立的 A 级证据，才可候选自动升级；
- 升级证据必须明确包含公司、产品或业务关系、产业链节点和有效时间；
- “布局”“关注”“可用于”等模糊表述不能独立支撑升级；
- 冲突证据进入人工复核，不静默覆盖旧结论；
- 降级、节点调整和失效必须保留原状态、新状态、原因、证据和时间。

### 5.3 商业化阶段

```text
概念相关 -> 技术研发 -> 样品/送样 -> 客户验证 -> 定点/供应商资格
-> 小批量 -> 量产 -> 明确订单 -> 收入确认 -> 收入占比显著提升
```

## 6. 映射变动类型

系统必须明确区分：

- `new_candidate`：首次发现公司与节点关系；
- `evidence_strengthened`：节点不变，新增更强证据；
- `status_upgraded`：映射状态从 `candidate` 升级为 `verified`；
- `node_adjusted`：从错误或宽泛节点转到更准确节点；
- `commercialization_advanced`：商业化阶段提升；
- `evidence_weakened`：证据过期、被否认或可信度下降；
- `status_downgraded`：映射状态降级；
- `mapping_invalidated`：业务退出或权威证据明确否定。

## 7. 变动重要性评分

每条变动计算 0–100 分：

| 维度 | 权重 |
|---|---:|
| 证据来源 | 25 |
| 商业化阶段 | 25 |
| 映射状态变化 | 20 |
| 业务贡献 | 15 |
| 节点重要性 | 10 |
| 时效与交叉验证 | 5 |

等级划分：

| 等级 | 分数 | 处理 |
|---|---:|---|
| P0 | 85–100 | 重大变化，消息首位 |
| P1 | 70–84 | 重要变化 |
| P2 | 50–69 | 一般但值得关注的变化 |
| P3 | 0–49 | 线索变化，只入候选与日志 |

至少存在一条 P0–P2 变动才发送飞书消息。同一公司的同一事件应合并，同一变动不得因重跑重复推送。

## 8. 龙头 Top3 排序

核心节点 Top3 采用产业证据排序，不以概念热度或当日股价排序：

| 维度 | 权重 |
|---|---:|
| 业务真实性及主营关联 | 25 |
| 商业化阶段 | 20 |
| 技术壁垒与国产替代 | 15 |
| 收入、订单和产能兑现 | 15 |
| 产业链节点重要性 | 10 |
| 证据质量与新鲜度 | 10 |
| 市场竞争地位 | 5 |

排序约束：

- `candidate` 可进入观察 Top3，但必须显示“候选”；
- 正式 Top3 原则上只接受 `verified`；
- 同一股票多个标签不简单累加；
- 缺失收入占比保持缺失，不当作 0 分；
- D 级来源不能独立支撑正式 Top3；
- 股价表现不直接改变产业龙头等级。

## 9. 快照、去重与数据保留

需要保存或复用：

- 分数据源刷新游标；
- 证据内容指纹；
- 映射状态变更历史；
- 每日成功快照；
- 核心节点 Top3 排名快照；
- 自动任务运行记录；
- 每个飞书群的发送状态和 `message_id`。

不覆盖旧记录。当前状态用于查询，追加式历史用于解释为何变化。变动指纹应包含产业链、公司、节点、证据事件、变动类型和目标状态，保证重跑幂等。

## 10. 飞书推送

### 10.1 目标群

- `ai_research_analysis`：AI 投研分析；
- `ai_research_test`：AI 投研测试；
- `fitness_group`：一起减肥吧。

### 10.2 消息内容

消息应包含：

1. 数据截止时间和本次扫描规模；
2. P0、P1、P2 变动数量；
3. 按重要性降序的变动详情；
4. 每条变动的公司、节点、前后状态、商业化阶段、证据来源、日期、分数和剩余风险；
5. L1–L8 覆盖变化和仍缺映射节点；
6. 龙头 Top3 进入、退出及原因。

消息必须明确说明：重要性分数衡量产业证据变动，不表示股价上涨概率。

### 10.3 送达与重试

- 三个群独立记录发送状态；
- 只有获得真实 `message_id` 才记为送达；
- 失败群在 5、15、30 分钟后重试；
- 已成功群不重复发送；
- 数据更新成功但飞书失败时，任务状态为“数据成功、推送未完成”，数据不回滚。

## 11. 失败处理与事务边界

### 11.1 数据源失败

- 单一来源失败不阻断其他来源；
- 本次运行记录不可用来源；
- 不根据不可用来源降级已有映射；
- 下次运行从该来源的旧游标继续补采。

### 11.2 映射更新失败

- 映射更新使用事务；
- 失败时不提交半成品映射；
- 不生成基于半成品数据的飞书消息。

### 11.3 重复触发

- 使用“任务类型＋日期”幂等锁；
- 同一时间只允许一个正式任务运行；
- 手工补跑复用已有批次和变动指纹，不重复推送。

## 12. 调度设计

- 每日北京时间 19:30 执行具身智能增量刷新，包括周末；
- 周末没有新行情时，明确使用最新交易日，不伪造当日行情；
- 每周日 20:30 执行全量一致性审计；
- 周审计只输出偏差、重复、缺口和建议，不自动覆盖正式映射；
- 周审计只有产生 P0–P2 实际变动时才推送。

## 13. 可观测性

每个批次至少记录：

- 批次 ID、调度时间、实际开始/结束时间；
- 每个数据源的新鲜度、读取数量和新游标；
- 新增、去重、冲突和被拒绝证据数量；
- 新增、升级、降级、调整和失效映射数量；
- L1–L8 覆盖率、空节点和重复节点；
- P0–P3 变动数量；
- 三个群的发送次数、最终状态和 `message_id`；
- 限制项、错误阶段和可补跑建议。

## 14. 测试与验收

### 14.1 单元测试

- 证据来源分级；
- 模糊表述不能触发自动升级；
- 一条 S 级或两条独立 A 级的升级规则；
- 证据指纹去重；
- 映射状态机；
- 变动重要性评分与 P0–P3 分级；
- 缺失值不被当作 0 分；
- 多标签不简单累加；
- 变动合并和幂等推送。

### 14.2 集成测试

- 从增量数据到映射快照的完整链路；
- 单一数据源失败时其他来源继续；
- 映射更新失败的事务回滚；
- 前后快照生成正确变动；
- 无 P0–P2 变动时不调用飞书发送；
- 三群独立发送、单群失败重试、成功群不重发；
- 获得 `message_id` 后才记为送达。

### 14.3 验收条件

1. 能够手工完整运行一次刷新；
2. 能够每天 19:30 自动运行；
3. 相同数据连续运行两次不产生重复证据、映射或飞书消息；
4. 新映射默认进入 `candidate/pending_review`；
5. 满足规则的权威证据可以正确升级；
6. 证据冲突不静默覆盖旧结论；
7. 能够识别新增、增强、升级、降级、节点调整和失效；
8. 能够输出 L1–L8 覆盖率、缺口和重复节点；
9. 能够输出核心节点 Top3 及变化原因；
10. 没有 P0–P2 变动时不发送飞书；
11. 有变动时分别发送到三个指定群；
12. 每个成功群都有真实 `message_id`；
13. 单群失败可重试，不重复发送成功群；
14. 任务失败后有明确日志和手工补跑入口；
15. 开发、测试和提交不包含当前工作树的无关改动。

## 15. 实施约束

- 优先复用现有 `supply_chain_hierarchy_nodes`、`business_tag_mapping`、`business_tag_evidence_events`、映射状态历史和调度器能力；
- 只在现有表无法表达游标、快照、变动指纹或推送送达状态时新增表；
- 所有迁移、刷新和审计入口支持预览模式，预览不写库、不发送飞书；
- 正式运行只基于上一次成功快照，失败批次不得成为新基线；
- 涉及投资与映射输出时保留证据等级、审核状态、时间截止和局限性。
