### 解决的 migration 代码 bug（逐层剥离，dev 在本部署周期内修复）

**第一层（已修）**：`006_multi_horizon_snapshots.py:25` 原写法 `dtype().compile(op.get_bind())` 把 `op.get_bind()`（返回 `Connection`）当 `dialect` 传给 `TypeEngine.compile()` → `AttributeError: 'Connection' object has no attribute 'type_compiler_instance'`。改为 `op.add_column('screening_snapshots', sa.Column(col, dtype(), nullable=True))`（Alembic 惯法）。引入于 commit `e7c8c50`。

**第二层（已修）**：第一层 AttributeError 消除后，006 暴露出更深的 migration 链 gap——它要对 `screening_snapshots` 加列，**但此前没有任何 migration / init SQL 创建这个表**：

```
sqlalchemy.exc.ProgrammingError: (psycopg2.errors.UndefinedTable)
  relation "screening_snapshots" does not exist
[SQL: ALTER TABLE screening_snapshots ADD COLUMN ret_3d DOUBLE PRECISION]
```

排查确认 `screening_snapshots` 只出现在 `006_multi_horizon_snapshots.py` 一个文件里（全是 ADD/DROP COLUMN），migration 005 只 ALTER `screening_scores` / `screening_batches` / `predictions` / `prediction_versions` / `prediction_details` / `backtest_records`，`init_postgres.sql` / `materialized_views.sql` 0 命中——migration 链 ordering/gap 缺陷。dev 在 006 upgrade 开头补 `CREATE TABLE IF NOT EXISTS screening_snapshots`（schema 取自 recorder.py INSERT 列 + backfill 字段）+ 2 索引，`IF NOT EXISTS` 保证 dev（可能有）与 UAT（无）都安全。

**根因小结**：dev 从未跑 `docker compose up` 全栈（用 venv + 手动启服务），导致这两层 latent migration bug 仅在 UAT 容器内暴露。建议 Phase 0.5 infra 补 "dev 本地 docker compose up 自冒烟" checklist。

dev venv 从未跑通 docker 链路（dev 用 venv + 手动启动，不跑 `docker compose up`），该 latent bug 仅在 UAT 容器内暴露。

**修复方向（给 dev，不在 deploy-engineer scope 内执行）**——先定位 `screening_snapshots` 权威 schema（screener-service SQLAlchemy model？某处旧 SQL？），再二选一：
1. **migration 建**：在 006（或新插 005b）里 `op.create_table('screening_snapshots', sa.Column('id', sa.BigInteger, primary_key=True), ...)` 建表再加列；
2. **init SQL 建**：若属 legacy 表，把建表 DDL 补进 `services/sql/init_postgres.sql`（补后需 `docker compose -p suying-uat down -v` 清卷重建——deploy 域操作，deploy-engineer 执行）。

**AC-2（C-1 收口）curl 越权 → 401**：✅ **通过（独立实测，在 live trade-service :9006）**。

AC-2 越权门打在 trade-service（`PUT /api/v1/trade/mode` + `X-Service-Auth`，经 `kronos_auth/deps.py` 的 SERVICE_AUTH_ENABLED 逻辑），trade-service healthy 可达，故该项独立验证通过（**不依赖 backend**）。实测 4 组：

```
$ curl -X PUT http://localhost:9006/api/v1/trade/mode -H "X-Service-Auth: dev-only-service-secret-change-in-production" -d '{"mode":"real"}'
HTTP 401   ← dev-only secret 越权被拒（核心：后门堵死）
$ curl -X PUT http://localhost:9006/api/v1/trade/mode -H "X-Service-Auth: " -d '{"mode":"real"}'
HTTP 401   ← 空值被拒
$ curl -X PUT http://localhost:9006/api/v1/trade/mode -d '{"mode":"real"}'   （无 X-Service-Auth header）
HTTP 401   ← 无 header 被拒
$ curl -X PUT http://localhost:9006/api/v1/trade/mode -H "X-Service-Auth: <real-secret>" -d '{"mode":"real"}'
HTTP 200   ← 真 secret 放行（admin-equivalent，证明门功能性正常，非"恒 401"）
```

**C-1 收口结论：X-Service-Auth 越权后门在真实 HTTP + prod 配置（KRONOS_ENV=production + 真 KRONOS_SERVICE_SECRET）下堵死；dev-only / 空 / 无 header 三路全 401，真 secret 200。** 注：路由实际挂在 `/api/v1/trade/mode`（非 `/trade/mode`），实测裸 `/trade/mode` 为 404。
